CI에서 앱 서명을 처리한 뒤, 평소 쓰던 Mac의 앱들을 사용할 때마다 다시 로그인해야 했습니다.

거부기린의 릴리즈 작업을 GitHub-hosted runner에서 기존 Mac의 self-hosted runner로 옮긴 뒤 겪은 일이었습니다. Actions 사용량 부담을 줄이려고 시작한 전환이었는데, 같은 Mac에서 개발과 CI를 함께 실행하면서 평소 쓰던 앱의 인증 상태에도 영향을 받았습니다.

## 저장소를 비공개로 바꾸자 작업이 시작되지 않았습니다

거부기린은 팀원들과 함께 개발하는 Tauri 기반 데스크톱 앱으로, Windows와 macOS를 지원합니다. GitHub Actions에서 코드 검증과 운영체제별 배포 파일 생성을 처리했고, macOS 릴리즈에는 앱 빌드 외에 서명과 패키징도 필요했습니다.

창업대회 제출과 외부 공개 범위를 관리하기 위해 저장소를 비공개로 전환한 뒤, Actions의 일부 작업이 시작되지 않았습니다.

`lint`, `typecheck`, `rust-check`, `prepare-release-matrix` 같은 작업이 코드 오류로 실패한 상황은 아니었습니다. 실행 환경을 배정받기 전에 차단됐고, GitHub가 남긴 안내는 결제 상태나 지출 한도를 확인하라는 내용이었습니다.

## 기존 workflow를 유지하면서 실행 장비를 바꿨습니다

GitHub Actions에 추가 결제하거나 지출 한도를 올리는 방법, CircleCI 같은 다른 CI 서비스를 도입하는 방법도 검토했습니다. hosted runner를 유지하면 환경 관리 부담은 적지만 macOS 빌드 비용이 남고, 다른 서비스로 옮기면 workflow를 이전해야 했습니다.

기존 Mac을 활용하면 GitHub Actions의 작업 흐름을 유지하면서 실행 장비를 바꿀 수 있었습니다. Mac을 저장소의 self-hosted runner로 등록하고, 검증·릴리즈 작업을 해당 장비로 보내도록 workflow의 실행 조건을 수정했습니다.

이제 해당 작업을 실행할 장비는 직접 마련했지만, 장비 상태와 빌드 도구, 서명 환경도 관리해야 했습니다. 가장 크게 시간을 쓴 부분은 macOS 앱 서명이었습니다.

## 서명 작업의 영향이 평소 쓰던 앱까지 이어졌습니다

별도 사용자 계정에서 runner를 실행하는 방법도 고려했지만, 실제로는 기존 개발 계정에서 운영했습니다. 사용하던 Mac에는 필요한 도구가 이미 설치돼 있었습니다.

Keychain은 인증서와 키 등을 보관하는 macOS 저장소입니다. 평소 사용하던 Keychain과 개발자 인증서용 Keychain은 달랐지만, 같은 사용자 환경에서 함께 다루고 있었습니다.

runner 작업 뒤에는 평소 쓰던 앱들의 인증 상태가 풀려 재로그인이 필요했습니다. CI의 영향이 릴리즈 빌드를 넘어 일상적인 앱 사용까지 이어진 것입니다. 같은 Mac에서 개발을 계속하려면 **작업이 끝난 뒤 남는 설정도 관리해야 했습니다.**

## 서명용 Keychain을 실행마다 만들었습니다

개발용 Keychain에 CI 서명 인증서를 계속 추가하는 대신, 실행마다 별도의 임시 Keychain을 만들고 인증서를 가져오도록 했습니다. 여러 실행이 같은 Keychain을 만들거나 삭제하지 않도록 이름도 실행마다 구분했습니다.

아래 코드는 현재 저장소의 서명 설정 스크립트에서 Keychain 생성·설정·잠금 해제 부분을 발췌한 것입니다. 인증서 가져오기와 상태 저장은 별도 단계에서 처리합니다.

```javascript
run('security', ['create-keychain', '-p', keychainPassword, keychainPath])
run('security', ['set-keychain-settings', '-lut', '21600', keychainPath])
run('security', ['unlock-keychain', '-p', keychainPassword, keychainPath])
```

생성한 Keychain 경로는 다음 단계로 전달하고, 자세 엔진·앱·DMG의 서명 명령에서 명시하도록 했습니다. 자세 엔진은 웹캠 영상으로 사용자의 자세를 분석하는 별도 Python 프로세스로, 앱과 함께 배포하는 서명 대상입니다.

다만 Keychain 파일을 따로 만드는 것만으로 공유 상태 문제가 모두 사라지지는 않았습니다.

## 검색 목록은 여전히 공유 설정이었습니다

인증서를 찾는 Keychain 검색 목록은 사용자 계정에서 공유합니다. Keychain 파일을 따로 만들어도 검색 목록을 바꾸는 작업은 같은 설정에 영향을 줬습니다.

작업 시작 전 목록을 저장했다가 종료할 때 통째로 복원하면, 그사이에 다른 작업이 추가한 Keychain까지 빠질 수 있었습니다.

그래서 정리할 때는 이전 목록을 그대로 덮어쓰는 대신, **현재 검색 목록에서 이번 실행의 Keychain만 제거하도록 구성했습니다.** 다른 작업이 추가한 항목과 유효한 기본 Keychain은 보존하도록 했습니다.

여러 작업이 동시에 목록을 읽고 수정하면서 서로의 변경을 덮어쓰지 않도록, 공유 설정을 변경하는 구간에는 잠금을 적용했습니다.

작업 A와 B가 각자의 Keychain을 추가하는 예시에서, A의 정리 방식을 바꾸며 목록의 차이를 확인할 수 있습니다.

현재 코드의 검색 목록 필터는 다음과 같습니다. 경로를 정규화하고 중복을 제거한 뒤, 지정한 Keychain과 존재하지 않는 항목을 제외합니다.

```javascript
export function sanitizeSearchList(paths, { removeKeychain = '' } = {}) {
  return uniqueKeychainList(paths).filter(path => {
    if (removeKeychain && sameKeychainPath(path, removeKeychain)) {
      return false
    }

    return keychainExists(path)
  })
}
```

정리 스크립트는 현재 목록과 `removeKeychain: signingKeychain`을 이 함수에 전달합니다. 목록을 읽고 변경하는 구간을 감싼 `withKeychainListLock`은 사용자별 공통 경로에 잠금 디렉터리를 만들어 잠금을 획득하고, `finally`에서 해제합니다.

정리 기준은 자원의 소유 범위였습니다. **이번 실행이 만든 Keychain과 인증 파일은 삭제하고, 공유 검색 목록과 기본 Keychain은 다른 작업의 상태를 보존하면서 변경했습니다.**

## 빌드가 실패해도 정리 절차를 실행했습니다

서명이나 패키징 중간에 실패해도 임시 자원을 정리하도록, 정리 절차를 별도 스크립트로 분리했습니다. 현재 workflow는 `always()`와 macOS 조건을 함께 사용합니다. 실행 위치는 job의 기본 설정인 `apps/desktop`입니다.

```yaml
- name: Cleanup Apple signing
  if: ${{ always() && startsWith(inputs.platform, 'macos') }}
  shell: bash
  run: node scripts/cleanup-tauri-apple-signing.mjs
```

정리 스크립트에서는 다음 작업을 수행하도록 했습니다.

1. 현재 검색 목록에서 이번 실행의 Keychain을 제거합니다.
2. 다른 작업의 항목을 보존하고, 유효한 기본 Keychain을 유지·복구합니다.
3. 이번 실행에서 만든 임시 Keychain을 삭제합니다.
4. 임시 인증서와 API 키 파일을 삭제합니다.

정리 스크립트에서 실행하는 `security` 명령은 실패 시 경고를 남기고 다음 처리를 이어가도록 했습니다. 다만 잠금 획득이나 파일 삭제 등 다른 처리에서 발생하는 예외까지 모두 이 방식으로 처리하는 것은 아닙니다.

서명 단계의 성공과 실패를 나눠 보면, 두 경우 모두 정리 절차로 이어집니다. 여기서 정리 단계의 실행과 실제 복구 성공 여부는 구분해야 합니다.

## 생성한 파일을 실제 다운로드 페이지까지 연결했습니다

기존 Mac에서 실행한 workflow로 서명된 앱과 DMG를 생성했고, 파일을 내려받아 실행되는 것까지 직접 확인했습니다. 배포 파일은 Cloudflare R2에 업로드한 뒤 거부기린 다운로드 페이지에 연결했습니다.

실행이 막혔던 검증·릴리즈 작업을 self-hosted runner로 옮기고 실제 배포까지 이어갔습니다. 다만 비용과 사용량의 전후 차이는 측정하지 않아 절감 폭은 알 수 없습니다.

## 현재 workflow의 검증과 배포 경로

팀원들과 함께 사용하는 저장소이므로 현재 구성의 검증·배포 실행 조건도 구분해 정리해 두었습니다. `develop`·`main` 대상 PR과 두 브랜치의 push에서는 CI workflow가 self-hosted runner에서 실행됩니다.

릴리즈 workflow는 `tauri-v*` 태그 push 또는 수동 실행으로 시작합니다. 다만 실제 릴리즈 빌드·업로드 job은 해당 태그에서만 진행하며, 수동 실행에서 `dry_run`을 선택하면 실행하지 않습니다. 업데이터의 `latest.json`은 태그 push 시 게시하고, 수동 실행에서는 `publish_updater_latest`를 선택해야 게시합니다.

서명·업로드 job이 사용하는 `release` 환경도 `tauri-v*` 태그만 허용하며, 필수 검토자 승인 규칙은 없습니다. 현재 구성은 태그와 실행 옵션으로 배포 경로를 구분합니다. PR 검증과 서명 작업의 실행 장비까지 격리한 구성은 아닙니다.

## 정리 단계가 끝났다고 복구까지 성공한 것은 아니었습니다

남은 과제는 정리 후 상태 검증입니다. `security` 명령의 실패를 경고로 남기고 다음 처리를 이어가므로, 스크립트가 끝났다는 사실만으로 자원 삭제와 설정 복구가 모두 성공했다고 볼 수는 없습니다.

다음에는 종료 후 실제 상태를 검사하고, 복구가 필요한 항목이 남으면 workflow 결과에 드러나도록 보완하고 싶습니다. 이번 실행의 Keychain이 검색 목록에서 빠졌는지, 임시 인증 파일이 삭제됐는지, 기본 Keychain과 다른 작업의 항목은 유효하게 남아 있는지를 확인하는 것입니다.

이번 전환에서 배운 것은 **runner 작업이 끝난 뒤 장비에 남는 상태까지 관리해야 한다**는 점입니다. 다음에 runner를 구성한다면 설치와 함께 세 가지를 먼저 정하려고 합니다.

- 무엇을 바꾸는가: 실행별 Keychain과 임시 인증 파일, 공유 검색 목록과 기본 Keychain.
- 무엇을 보존하는가: 개발용 Keychain과 다른 작업이 사용하는 항목.
- 종료 후 무엇을 확인하는가: 이번 실행의 자원 삭제 여부, 기본 Keychain의 유효성, 다른 작업의 항목 보존 여부.
