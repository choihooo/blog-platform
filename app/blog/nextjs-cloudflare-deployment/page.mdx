친구를 위한 가계부를 만들었습니다. 친구 혼자 사용할 앱이라 휴대폰에서 쓰기 편하게 만드는 것을 기준으로 잡았습니다. 앱은 Cloudflare Workers와 D1으로 구성했고, 토스 시세를 가져오는 중계 서버는 Oracle Cloud에 따로 두었습니다.

D1에 지출을 저장하는 코드와 토스 시세를 가져오는 코드를 어디에서 실행할지 정하는 과정에서, 프레임워크·배포 환경·어댑터의 역할을 나눠 보게 됐습니다.

## 1. 가계부를 배포하며 헷갈렸던 이름들

Workers를 쓰면 Pages도 함께 필요한지, OpenNext를 위해 서버를 더 띄워야 하는지 궁금했습니다. Next.js로 작성한 서버 코드는 실제로 어디에서 실행되고 D1에는 어떻게 연결될까요?

친구가 지출을 입력하고 저장 버튼을 누르는 상황부터 생각해 봤습니다. 휴대폰에서 보낸 요청은 어디로 가고, 어떤 코드가 실행되어 D1에 기록할까요? 이 요청을 기준으로 프레임워크와 실행 환경을 나눴습니다.

실제 가계부 화면에 예시 거래와 시세를 넣었습니다. 거래를 입력하거나 수정하면 월별 결산에 반영됩니다. 변경 내용은 이 데모에서만 유지되며, 초기화하거나 새로고침하면 예시 데이터로 돌아갑니다.

## 2. 프레임워크·실행 환경·DB의 역할

먼저 이번 앱의 기본 구성만 놓고 역할을 나눠 봤습니다. 코드를 작성하는 도구와, 그 코드를 실행하고 데이터를 저장하는 곳을 구분하면 됩니다.

| 도구 | 이번 앱에서 하는 일 |
| --- | --- |
| Next.js | 화면과 지출 저장·조회 코드를 작성합니다. |
| Workers | 앱 화면을 제공하고 서버 코드를 실행합니다. |
| OpenNext | Next.js 빌드 결과를 Workers에 맞게 바꿉니다. |
| D1 | 지출 내역과 앱 데이터를 저장합니다. |

Next.js로는 화면과 페이지 이동뿐 아니라 서버에서 데이터를 조회하거나 저장하는 코드도 같은 프로젝트 안에 작성할 수 있습니다. 그래서 프로젝트 안에 브라우저에서 동작할 코드와 서버에서 실행할 코드가 함께 들어갈 수 있습니다.

가계부에서 금액을 입력하고 버튼을 누르는 상호작용은 브라우저가 처리합니다. 저장 요청을 받아 입력값을 검증하고 DB에 기록하는 일은 서버 코드가 맡습니다. 배포·실행 환경은 앱의 파일을 사용자에게 전달하고, 서버 처리가 필요한 요청에 코드를 실행할 곳입니다.

## 3. Pages·Workers·Vercel의 저장 요청 경로

친구가 금액과 날짜를 입력하고 저장 버튼을 눌렀다고 해 보겠습니다. D1을 계속 쓴다는 전제에서, 화면을 제공하는 곳과 저장 요청을 처리하는 곳을 비교했습니다. 아래는 각 서비스에서 생각해 본 구성 예시입니다.

<DeploymentComparison />

### Pages에 정적 화면과 저장 API를 배포하는 경우

Next.js 화면을 정적 파일로 내보내 Pages에 올릴 수 있습니다. 빌드할 때 만든 HTML·CSS·JavaScript를 전달하는 방식입니다. 이 정적 내보내기에는 요청이 올 때마다 실행하는 Next.js 서버 기능이 포함되지 않습니다. 지출을 저장하는 Server Action이나 요청 시점의 SSR을 그대로 실행할 수는 없습니다.

서버 코드는 Pages Functions로 작성할 수 있습니다. 저장 요청을 받는 API에 D1을 연결하면, 정적으로 배포한 화면이 이 API를 호출하게 됩니다.

Functions를 추가한다고 정적 빌드에서 빠진 Next.js 서버 기능이 자동으로 연결되는 것은 아닙니다. 이 구성에서는 Pages Functions API를 별도로 작성합니다.

### Workers에서 Next.js 서버 코드와 D1을 연결하는 경우

Workers는 서버 코드와 정적 파일을 함께 배포할 수 있어 Pages를 반드시 따로 둘 필요가 없습니다. 정식 Next.js를 유지하면서 Workers에 배포하는 방법으로 OpenNext의 Cloudflare 어댑터를 사용할 수 있습니다.

저장 요청을 처리하는 Next.js 서버 코드는 Workers에서 실행됩니다. D1 바인딩을 설정하면 이 코드에서 DB에 접근할 수 있습니다. 바인딩은 실행 중인 코드가 사용할 D1 같은 자원을 연결하는 설정입니다.

D1 접근용 API 서비스를 별도로 분리할 필요는 없습니다. 이번 앱에 따로 둔 Oracle 서버는 토스 시세를 조회하는 중계 서버입니다.

### Vercel에서 Next.js를 실행하고 D1에 접근하는 경우

Vercel에 배포하면 Next.js의 서버 처리는 Vercel의 실행 환경이 맡습니다. 예를 들어 요청마다 화면을 만드는 SSR은 Vercel Functions에서 실행됩니다.

D1을 유지한다면 연결 방법을 따로 정해야 합니다. Workers 안에서 사용하는 D1 바인딩을 Vercel 서버 코드에 그대로 붙이는 구조는 아니기 때문입니다. 한 가지 설계 예시는 D1에 접근하는 Worker API를 두고 Vercel 서버 코드가 HTTP로 호출하는 방식입니다.

이 흐름은 가능한 설계 예시이며 Vercel에서 D1을 사용하는 유일한 방법은 아닙니다. 이 경우에는 Vercel과 Worker 사이의 API 요청·응답, 인증, 오류 처리도 설계해야 합니다.

## 4. OpenNext가 빌드 결과를 Workers에 맞추는 과정

OpenNext의 Cloudflare 어댑터는 Next.js 빌드 결과를 Workers에서 실행할 수 있는 형태로 바꿉니다. 실제로는 OpenNext의 빌드 명령이 Next.js 빌드와 변환을 이어서 수행할 수 있습니다.

<BuildAndRequestFlow />

친구가 저장 버튼을 누를 때는 이미 빌드와 배포가 끝나 있습니다. 그때마다 앱 전체를 변환하는 것이 아니라, Workers에 배포된 코드가 요청을 받아 저장 로직을 실행하고 D1에 기록합니다.

OpenNext 자체를 위해 별도로 운영할 서버가 하나 더 생기지는 않습니다. 이번 프로젝트의 Oracle 서버는 토스 API를 호출하기 위해 둔 서버입니다.

빌드 결과를 변환하더라도 Workers의 실행 환경이 일반적인 Node.js 서버와 완전히 같아지지는 않습니다. Node.js의 특정 기능에 의존하는 패키지와 사용하는 Next.js 기능은 버전별 지원 범위를 확인해야 합니다.

실제로 시세 중계 호출을 검증하던 당시, Workers 런타임에서 `fetch`의 `redirect: "error"` 옵션이 지원되지 않아 호출이 실패했습니다. Workers 런타임으로 호출 코드를 실행하는 테스트에서 재현한 뒤, `redirect: "manual"`로 바꾸고 3xx 응답을 실패로 처리했습니다.

Next.js 개발 서버에서 화면이 뜬 뒤에는 Workers 런타임 미리보기에서 D1 저장·조회를 확인했습니다. 실제 Workers에 배포한 뒤에도 HTTPS 화면과 가계부 API의 읽기·쓰기를 확인했습니다.

## 5. OpenNext와 vinext의 빌드 방식 차이

vinext는 Next.js API를 Vite 기반으로 다시 구현한 도구입니다. 기존 프로젝트의 디렉터리 구조와 코드 사용 방식을 최대한 유지하면서 개발과 빌드에는 Vite 기반 도구를 사용합니다. OpenNext와는 앱을 빌드하는 기반이 다릅니다.

| 구분 | OpenNext의 Cloudflare 어댑터 | vinext |
| --- | --- | --- |
| 접근 방식 | 정식 Next.js 빌드 결과를 변환 | Next.js API를 Vite 기반으로 재구현 |
| 개발·빌드 기반 | Next.js | Vite 기반 도구 |
| 도입할 때 확인할 것 | Next.js 버전·기능과 Workers 환경의 호환성 | 사용하는 Next.js API·설정·패키지의 호환성 |

Next.js API를 재구현했다는 설명이 모든 앱의 무수정 호환을 보장하지는 않습니다. 가계부에서 사용하는 라우팅, 서버 저장·조회 기능, 패키지와 설정의 호환성을 확인해야 합니다. OpenNext도 사용하는 기능과 패키지가 Workers 환경에서 지원되는지 검증해야 합니다.

2026년 11월 17일 확인한 Cloudflare 문서는 vinext를 Workers에서 Next.js 앱을 실행하는 기본 경로로 권장하면서 beta라고 명시했습니다. 기존 운영 앱에 도입하기 전 호환성 검사와 지원 현황을 확인하도록 안내합니다.

처음 정한 조건은 Next.js의 서버 기능을 같은 앱에서 사용하고, D1은 서버 코드에서만 접근하는 것이었습니다. 이 조건을 유지하면서 Next.js 서버와 D1을 Workers에 함께 두는 경로로 OpenNext를 선택했습니다. 프레임워크를 재구현한 도구로 바꾸기보다, 정한 스택을 배포 환경에 연결하는 데 범위를 맞춘 선택입니다. vinext와 성능·안정성을 직접 비교한 결과는 아닙니다.

## 6. Workers·D1과 Oracle 시세 중계 서버의 전체 구성

D1에 접근하는 가계부 서버는 Workers에, 고정 출발 IP가 필요한 토스 호출은 Oracle에 두었습니다. Workers는 화면과 가계부 API를 제공하고, Oracle의 Node.js 서버는 토스 시세 조회를 중계합니다.

### 가계부 저장과 토스 시세 조회

지출을 입력하면 먼저 휴대폰의 IndexedDB에 저장하고, 온라인에서 Workers의 가계부 API를 통해 D1에 동기화합니다. 이 과정에는 Oracle이나 토스 API가 관여하지 않습니다.

주식은 종목·수량·평균 매입단가를 직접 등록합니다. 종목 검색이나 현재가 조회가 필요할 때 Workers가 Oracle 중계 서버를 HTTPS로 호출합니다. Caddy가 요청을 받아 Node.js 중계 서버로 전달하고, 중계 서버가 토스 API를 호출해 결과를 돌려줍니다. 계좌·보유자산·주문 API를 연결한 구성은 아닙니다.

토스 Client ID·Secret과 인증 토큰은 Oracle 중계 서버에서 관리합니다. Workers에는 중계 서버 주소와 중계 인증용 비밀값만 둡니다. 중계 서버는 토큰을 프로세스 안에서 공유하고, 현재가 응답은 60초, 종목 목록은 하루 동안 캐시합니다.

Workers는 등록한 주식의 마지막 성공 시세를 D1에 저장합니다. 유효한 캐시가 있으면 재사용하고, 외부 조회에 실패하면 마지막 시세와 오류 안내를 반환합니다. 브라우저도 마지막 시세를 IndexedDB에 보관합니다. 오프라인에서는 기존 값을 유지하되 조회 시점을 구분해야 합니다.

### 배포 과정과 확인한 범위

앱은 Next.js 빌드 결과를 OpenNext로 변환해 Workers에 배포합니다. 중계 서버는 Oracle VM에 Node.js 코드를 올려 systemd 서비스로 실행하고, Caddy가 HTTPS 요청을 받아 전달합니다.

2026년 11월 16일 앱과 중계 서버를 배포하고, 운영 Workers에서 국내·미국 종목 검색을 확인했습니다. Oracle 중계 서버에서는 삼성전자와 애플의 실제 현재가를 받았습니다. 당시 운영 가계부에는 등록된 주식이 없어 앱의 시세 API는 빈 배열을 반환했습니다. 확인한 범위는 중계 서버의 가격 응답까지이며, 앱에 등록한 주식의 가격 표시까지 검증한 것은 아닙니다.

실제 휴대폰 설치·재실행과 장기 비용·성능은 별도 확인이 필요합니다. 현재 구성의 비용 절감이나 성능 우위를 측정한 결과는 없습니다.

## 7. PWA 설치와 오프라인 저장·동기화

PWA로 설치할 수 있게 만드는 것만으로 인터넷이 끊겼을 때의 동작까지 해결되지는 않습니다. 화면을 여는 데 필요한 파일과 응답은 서비스 워커와 캐시를 사용해 보관했습니다. 서비스 워커는 브라우저에서 네트워크 요청과 캐시를 다루는 기능이며, Cloudflare Workers와는 별개입니다.

지출 내역은 IndexedDB에 먼저 저장하고 온라인에서 D1에 자동 동기화하도록 구현했습니다. 개별 요청을 쌓는 큐 대신, 현재 가계부 전체 데이터와 미전송 상태·변경 ID·서버 버전을 관리합니다.

1. 입력한 지출과 미전송 상태를 IndexedDB에 저장합니다.
2. 온라인에서 가계부 데이터와 변경 ID·기준 서버 버전을 Workers의 가계부 API로 보냅니다.
3. 서버가 변경 ID와 기준 버전을 확인하고 D1에 저장합니다.
4. 성공 응답을 받은 변경의 동기화를 완료 처리합니다.

서버는 같은 변경 ID의 재전송을 확인합니다. 기준 버전이 달라졌다면 덮어쓰지 않고 충돌을 반환하며, 앱에서는 사용할 데이터를 선택하도록 했습니다. 시세도 마지막 성공 값을 IndexedDB에 보관하므로 인터넷이 끊겼을 때는 기존 시세와 조회 시점을 기준으로 사용합니다.
