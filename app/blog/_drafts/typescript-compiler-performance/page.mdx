## 빌드가 빨라졌는데, 이유를 설명하지 못했습니다

인턴 시절 SaaS 어드민에 새로운 기능을 추가하면서 필요한 라이브러리를 설치한 적이 있습니다. 당시 프로젝트의 TypeScript 버전이 오래돼 최신 라이브러리와 호환되지 않았고, 이를 계기로 3.x에서 5.x대로 마이그레이션했습니다.

작업을 마치고 master 브랜치에 머지한 뒤 CodePipeline을 확인했는데, 빌드가 전보다 빨라진 것처럼 느껴졌습니다. 코드에서 바꾼 부분은 `any`를 더 구체적인 타입으로 바꾼 정도였습니다. 설정도 일부 수정했지만, 어떤 변경이 속도에 영향을 줬는지 설명하려니 막혔습니다.

컴파일러 버전의 영향을 확인하려고 별도 프로젝트에서 코드와 설정을 고정한 채 TypeScript 3.9와 5.8을 비교했습니다. 클린 빌드는 6.7%, 증분 빌드는 14.1% 빨라졌고, 내부 진단에서는 Check보다 Emit 시간의 감소가 더 컸습니다. 이 결과를 읽는 데 필요한 컴파일 과정부터 살펴봤습니다.

## TypeScript 컴파일 과정

<CompilerPipelineDemo />

위 흐름도는 컴파일러의 역할을 나눈 것입니다. 실제로는 Program을 구성하면서 파일을 읽고 파싱하며, 타입 정보도 필요할 때 계산합니다.

### Program: 컴파일 대상 구성

`tsc`는 `tsconfig.json`과 실행 옵션을 바탕으로 컴파일 대상과 설정을 정합니다. 루트 파일에서 시작해 `import`나 참조를 따라가면 프로젝트의 의존 관계가 만들어집니다. A.ts가 B.ts를 가져오고 B.ts가 C.ts를 가져온다면, 필요한 파일들을 함께 살펴봐야 합니다.

Program은 이렇게 모인 소스 파일과 컴파일 옵션을 다루는 단위입니다. 파일 하나의 문법만 보는 것으로는 다른 파일에서 가져온 타입을 검사할 수 없기 때문에, 프로젝트 전체를 연결해 보는 과정이 필요합니다.

<DependencyDemo />

의존 관계가 넓어지면 읽고 분석할 파일도 늘어날 수 있습니다. 포함되는 파일은 설정과 모듈 해석 결과에 따라 정해집니다.

### Parsing: 텍스트에서 AST로 변환

스캐너는 소스 텍스트에서 토큰을 읽고, 파서는 문법에 맞춰 토큰을 조합해 추상 구문 트리(AST)를 만듭니다.

예를 들어 `const count: number = 1;`은 키워드·이름·타입·값 등의 토큰으로 나뉩니다. 파서는 이를 변수 선언으로 묶고, 이름은 `count`, 타입은 `number`, 초기값은 `1`이라는 구조를 AST에 담습니다.

이 트리가 있어야 뒤 단계에서 변수 선언과 함수 호출을 구분하고, 타입을 검사하거나 JavaScript로 변환할 수 있습니다.

### Binding: 이름과 선언 연결

같은 이름도 선언된 위치에 따라 다른 변수를 가리킬 수 있습니다.

```ts
const value = 1;

function printValue() {
  const value = "inside";
  console.log(value);
}
```

바인더는 선언을 심볼(Symbol)로 연결하고 스코프를 구성합니다. 위 예시의 두 `value`는 이름은 같지만 서로 다른 선언입니다. 타입 체커는 이 심볼과 스코프 정보를 이용해 어떤 선언을 참조하는지 확인합니다.

<ScopeDemo />

### Check: 타입 추론과 호환성 검사

타입 체커는 표현식의 타입을 구하고, 대입이나 함수 호출이 허용되는지 검사합니다. 이미 계산한 정보를 재사용하기도 합니다.

TypeScript는 구조적 타이핑을 사용합니다. 대입받는 쪽에 필요한 속성을 갖췄는지, 각 속성의 타입이 호환되는지 확인합니다.

<CompatibilityDemo />

타입 관계가 복잡해지면 검사할 조합도 늘어날 수 있습니다. 각각 멤버가 네 개인 두 유니온을 모두 교차 비교한다면 `4 × 4 = 16`개 조합이 생깁니다. 실제 검사 비용은 캐시와 최적화의 영향도 받습니다.

<TypeCheckDemo />

복잡한 추론 결과에 타입을 명시하면 계산이나 선언 파일 출력에 필요한 작업을 줄일 수 있습니다. 초기값이 명시한 타입에 맞는지 검사하는 작업은 여전히 필요합니다.

### Emit: 변환과 결과물 출력

Emit에서는 설정에 따라 JavaScript, 선언 파일(`.d.ts`), 소스맵 등을 생성합니다. 타입 주석은 JavaScript에서 제거되고, `target` 등에 따라 문법 변환도 일어납니다.

```ts
// 입력
const count: number = 1;
```

```javascript
// JavaScript 출력 예시
const count = 1;
```

<EmitOutputsDemo />

일반적인 `tsc` 실행에서는 타입 오류가 있어도 출력물이 생성될 수 있습니다. `noEmitOnError`의 기본값이 `false`이기 때문입니다. 아래 데모는 일반 `tsc` 실행에서 이 옵션에 따라 출력 여부가 달라지는 모습을 보여줍니다. `tsc -b` 빌드 모드는 범위에 포함하지 않습니다.

출력 작업을 줄일 때는 필요한 산출물을 먼저 확인해야 합니다. 선언 파일은 라이브러리 배포나 Project References에 필요할 수 있고, 소스맵은 디버깅에 쓰입니다.

## 같은 코드와 설정으로 버전 비교

전체 빌드 시간에는 파일 읽기, 파싱, 타입 검사, 출력, 증분 정보의 재사용 판단이 함께 반영됩니다. 어느 작업이 빨라졌는지 보려면 단계별 시간도 필요했습니다.

실험은 **동일한 코드와 설정에서 TypeScript 버전만 바꿨을 때의 차이**를 확인하도록 구성했습니다. 실무 프로젝트에서 `any`나 설정을 바꾼 효과는 이 실험으로 구분할 수 없습니다.

### 실험용 프로젝트

pnpm 모노레포와 Project References를 사용하고, 세 패키지로 구성했습니다. 비교 버전은 저장소에 기록된 TypeScript **3.9.5와 5.8.3**입니다.

| 패키지 | 역할 |
| --- | --- |
| `packages/core` | 공통 타입과 유틸리티 |
| `packages/ui` | core를 참조하는 제네릭 컴포넌트 타입과 복잡한 타입 정의 |
| `packages/app` | core와 ui를 가져와 사용하는 앱 |

주요 참조 흐름은 `core → ui → app`이며, app은 core도 직접 참조합니다. 타입 정의가 여러 패키지를 거쳐 사용되는 상황을 축소해 구성한 것입니다.

클린 빌드와 증분 빌드를 각각 5회 반복해 중앙값을 비교했습니다. 측정 당시의 CPU, 운영체제, Node.js 버전은 기록에 남아 있지 않습니다. 아래 결과는 당시 측정값이며 새로 측정한 값은 아닙니다.

### 측정 범위와 실행 방법

전체 실행 시간은 `/usr/bin/time -p`의 `real` 값으로 측정했습니다.

클린 빌드는 빌드 산출물과 증분 정보를 제거한 뒤 실행했습니다. OS 파일 시스템 캐시는 초기화하지 않았습니다. 증분 빌드는 초기 빌드 후 app 파일을 한 줄 변경하고 다시 실행했습니다.

컴파일러 내부에서는 다음 명령으로 단계별 시간을 확인했습니다.

```bash
tsc -b -v --extendedDiagnostics
```

내부 진단에서는 Parse, Bind, Check, Emit/print 시간을 확인했습니다. 프로세스 시작과 모듈 로딩 등이 포함된 외부 `real` 시간과는 측정 범위가 달라 별도로 비교했습니다.

실험 저장소에는 버전별 실행 스크립트가 있습니다.

```bash
# 클린 빌드
pnpm bench:ts3
pnpm bench:ts58

# 증분 빌드
pnpm bench:incremental:ts3
pnpm bench:incremental:ts58
```

## 결과: 클린 빌드 6.7%, 증분 빌드 14.1% 단축

기록한 결과에서는 TypeScript 5.8이 두 경우 모두 빨랐고, 상대적인 개선율은 증분 빌드에서 더 컸습니다.

| 구분 | TS 3.9 중앙값 | TS 5.8 중앙값 | 단축률 |
| --- | --- | --- | --- |
| 클린 빌드 | 2.54s | 2.37s | 6.7% |
| 증분 빌드 | 1.28s | 1.10s | 14.1% |

단축률은 `(기존 시간 - 변경 후 시간) / 기존 시간 × 100`으로 계산했습니다. 클린 빌드는 약 0.17초, 증분 빌드는 약 0.18초 줄었습니다. 절대 시간 차이는 비슷하지만 증분 빌드의 기준 시간이 짧아 상대적인 개선율이 더 크게 나타납니다.

### Check보다 크게 줄어든 Emit 시간

내부 진단에서 core와 ui는 출력 쪽의 비중이, app은 타입 검사 쪽의 비중이 두드러졌습니다.

| 항목 | TS 3.9 | TS 5.8 |
| --- | --- | --- |
| ui Emit/print | 0.36s | 0.12s |
| app Check | 0.32s | 0.21s |
| 전체 Check | 0.53s | 0.47s |
| 전체 Emit | 0.83s | 0.42s |

<PhaseTimingChart />

전체 Check 시간은 0.06초, Emit 시간은 0.41초 감소했습니다. 이 프로젝트에서는 출력 단계의 감소가 더 컸습니다. 개별 컴파일러 변경의 기여도는 따로 측정하지 않았으므로, 어떤 최적화가 이 차이를 만들었는지는 확인하지 못했습니다.

### 증분 빌드에서 달라지는 작업 범위

증분 빌드는 이전 빌드 정보를 이용해 다시 해야 할 일을 줄입니다. `.tsbuildinfo`에는 다음 빌드에 재사용할 프로젝트 정보가 저장되고, Project References의 빌드 모드는 참조 관계에 따라 필요한 프로젝트를 처리합니다.

app 파일을 바꾼 뒤 다시 검사하거나 출력할 대상은 변경 내용과 의존 관계에 따라 달라집니다. 이번 측정에서는 재빌드 작업과 변경 여부 판단에 걸린 시간을 분리하지 않아, 어느 쪽이 단축에 더 기여했는지는 알 수 없습니다.

## 프로젝트에 적용할 진단과 설정

빌드가 느릴 때는 다음 명령으로 단계별 시간을 확인할 수 있습니다.

```bash
tsc --extendedDiagnostics
```

Project References를 사용한다면 `tsc -b -v --extendedDiagnostics`로 확인합니다. Parse·Bind·Check·Emit 중 시간이 많이 드는 작업을 찾고, 변경 전후에 같은 항목을 비교합니다.

### 검사 생략과 증분 정보 재사용

```json
{
  "compilerOptions": {
    "skipLibCheck": true,
    "incremental": true,
    "tsBuildInfoFile": "./.tsbuildinfo"
  }
}
```

`skipLibCheck`는 선언 파일의 타입 검사를 생략합니다. 선언 파일은 여전히 읽으며, 생략한 검사에서 발견할 수 있었던 오류를 놓칠 수 있습니다.

`incremental`은 이전 빌드 정보를 저장해 다음 빌드에 활용하고, `tsBuildInfoFile`은 그 저장 위치를 정합니다. Project References를 사용한다면 참조 관계와 필요한 산출물도 함께 확인해야 합니다.

이번 비교 이후에는 버전을 올렸을 때 전체 빌드 시간과 내부 진단 값을 함께 확인하려 합니다. 시간이 줄어든 단계를 찾은 뒤, 해당 프로젝트에서 효과가 있었던 변경을 좁혀가는 방식으로 측정할 생각입니다.
