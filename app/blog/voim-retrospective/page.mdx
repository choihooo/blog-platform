## VOIM, 읽기 어려운 쇼핑 페이지를 바꿔보자

쇼핑 페이지에는 읽어야 할 정보가 많습니다. 상품 이름과 가격부터 옵션, 상세 설명까지 확인해야 합니다. 그런데 글자가 작거나 배경과 잘 구분되지 않으면 이 정보를 읽기 어렵습니다. 이미지 안에 들어간 설명은 브라우저의 글자 크기 설정만으로 조절하기도 어렵습니다.

VOIM은 이런 어려움을 겪는 저시력 사용자의 웹 쇼핑을 돕기 위해 만든 Chrome 확장 프로그램입니다. 사용하던 쇼핑 페이지 위에서 플로팅 버튼을 눌러 글자 크기와 굵기, 화면 대비를 조절할 수 있도록 했습니다. 이미지 속 글자는 OCR로 인식하고, TTS로 내용을 들을 수 있는 기능도 함께 제공했습니다.

Chrome 확장 프로그램 개발은 처음이었습니다. 다른 웹사이트 위에 우리가 만든 도구를 띄우고, 그 페이지의 내용을 바꾼다는 점이 흥미로웠습니다. 익숙하지 않은 개발 방식이었지만, 새로운 영역에 도전해보고 싶어 프로젝트에 참여했습니다.

저는 플로팅 버튼과 설정 메뉴를 비롯해, UI를 iframe 안에서 실행하는 구조와 페이지 사이의 메시지 통신을 맡았습니다. 사용자가 선택한 읽기 설정을 저장하고 새로고침이나 콘텐츠 변화 이후에도 다시 적용하는 처리, 키보드로 설정을 이동하고 닫은 뒤 원래 메뉴 버튼으로 돌아오는 포커스 처리도 구현했습니다. 개발하면서는 설정 화면을 만드는 일에 더해, 그 도구를 사용하는 동안에도 원래 쇼핑 페이지를 계속 이용할 수 있도록 신경 써야 했습니다.

## 처음 만드는 Chrome 확장 프로그램

이전까지는 제가 만든 페이지 안에 UI를 배치했습니다. VOIM은 이미 다른 사람이 만든 쇼핑 페이지 위에서 동작해야 했습니다. 개발을 시작하면서 먼저 Chrome 확장 프로그램이 어떤 구조로 실행되는지 살펴봤습니다.

확장 프로그램의 화면과 이벤트 처리, 웹페이지를 변경하는 코드가 서로 다른 실행 공간에 나뉘어 있었습니다. Background는 웹페이지의 DOM에 직접 접근할 수 없고, 페이지를 읽거나 수정하는 작업은 Content Script가 맡습니다. 필요한 정보를 주고받을 때는 메시지 통신을 사용합니다.

<ExtensionStructure />

VOIM에서는 사용자가 쇼핑하는 도중 설정을 바로 바꿀 수 있도록, 페이지 위에 플로팅 버튼과 설정 메뉴를 띄웠습니다. 이 메뉴는 툴바에서 여는 Popup과는 다른 UI였습니다. 사용자가 메뉴에서 글자 크기를 선택하면, 그 값을 실제 쇼핑 페이지에 적용하는 처리가 이어져야 했습니다.

처음에는 쇼핑 페이지 안에 React UI를 직접 삽입하는 방식으로 시작했습니다. 익숙한 React로 화면을 만들 수 있었지만, 설정 UI와 페이지를 변경하는 코드를 연결하는 과정은 새로 익혀야 했습니다. 초기 구현에서는 클릭해도 반응하지 않는 문제를 겪었고, 이후 설정 UI를 별도의 HTML 문서인 iframe 안에서 실행하는 구조로 옮겼습니다.

화면을 만드는 데서 시작한 작업이었지만, 개발을 이어가려면 각 코드가 어디에서 실행되고 무엇에 접근할 수 있는지부터 이해해야 했습니다.

## 복지센터에서 직접 사용해 보니

VOIM을 개발하면서 실제 사용자의 반응을 확인하기 위해 복지센터를 방문했습니다. 현장에서는 사용자와 함께 상품을 검색하는 단계부터 구매까지의 흐름을 진행했습니다. 그 과정에서 사용 후기를 듣고, 작업에 걸리는 시간도 측정했습니다.

측정 결과, 구매 흐름에 걸린 시간이 286초에서 146초로 줄어 약 49% 단축됐습니다.

당시 비교 대상에는 화면을 확대하거나 TTS로 내용을 읽어주는 기존 저시력 보조 프로그램이 있었습니다. VOIM은 사용 중인 쇼핑 사이트 안에서 글자 크기와 대비를 조절하고, 필요한 내용을 음성으로 들으며 쇼핑을 이어갈 수 있도록 만들었습니다.

현장에서는 사이트 안에서 이 과정을 한 번에 진행할 수 있어 편하다는 반응을 들었습니다. 실제로 이런 서비스가 있으면 좋겠다는 의견도 있었습니다.

확대나 TTS는 기존에도 있던 기능이었습니다. 사용자의 반응을 통해, 그 기능들을 쇼핑 흐름 안에서 함께 이용할 수 있다는 점에도 의미가 있음을 확인할 수 있었습니다. 상품을 찾고 정보를 읽고 구매하기까지, 필요한 도움을 같은 사이트 안에서 받을 수 있다는 것이 VOIM의 장점이었습니다.

## 페이지에 직접 넣었던 UI를 iframe으로 옮기기까지

처음에는 쇼핑 페이지 안에 `div`를 만들고, 그 안에 React로 만든 플로팅 버튼과 설정 메뉴를 표시했습니다. 콘텐츠 스크립트에서 컨테이너와 스크립트를 페이지에 삽입하고, 삽입한 스크립트가 React UI를 렌더링하는 방식이었습니다.

하지만 화면에 UI가 나타나도 클릭했을 때 반응하지 않는 문제가 있었습니다. 당시에는 이 문제를 겪은 뒤, UI를 별도의 HTML 문서인 iframe 안에서 실행하는 구조로 변경했습니다. React 앱의 진입점을 iframe 문서로 옮기고, 빌드 설정과 확장 프로그램의 리소스 등록도 함께 수정했습니다.

회고를 위해 당시 코드를 다시 살펴보니, 클릭 무반응도 구분해서 볼 필요가 있었습니다. 내부 설정 항목에는 아직 클릭 핸들러가 연결되지 않은 부분이 있었습니다. 반면 메뉴를 여는 플로팅 버튼에는 클릭 핸들러와 상태 변경 코드가 연결돼 있었습니다. 설정 항목의 미구현과 플로팅 버튼의 무반응을 같은 문제로 설명할 수는 없었습니다.

다른 페이지에 삽입한 React UI가 호스트 페이지의 이벤트 처리에 영향을 받는 사례도 찾아봤습니다. 다만 그것이 VOIM에서 발생한 원인인지는 확인하지 못했습니다. 당시 증상과 iframe으로 구조를 바꾼 기록은 남아 있지만, 클릭이 어느 단계에서 막혔는지까지 좁히지 못한 점은 아쉬움으로 남습니다.

iframe으로 전환하는 과정에서는 또 다른 문제가 생겼습니다. 메뉴를 닫았는데도 원래 쇼핑 페이지를 클릭할 수 없었습니다. 내부 메뉴는 사라졌지만, 투명한 iframe이 여전히 화면 전체를 덮고 있었기 때문입니다. 메뉴가 보이지 않는 것과 실제로 클릭을 받는 영역이 사라지는 것은 별개였습니다.

이를 해결하기 위해 메뉴를 열거나 닫을 때 `postMessage`로 `RESIZE_IFRAME` 메시지와 열림 여부를 바깥 페이지에 전달했습니다. 바깥에서는 메시지를 받아 메뉴가 열리면 iframe을 전체 화면으로 확장하고, 닫히면 플로팅 버튼 영역인 65×65px로 줄이도록 했습니다. 축소된 영역 안에 버튼이 표시되도록 내부 배치도 함께 조정했습니다.

수정 후에는 메뉴를 닫고 원래 쇼핑 페이지의 요소를 클릭할 수 있는지 직접 확인했습니다. 이 과정에서 UI 자체의 동작뿐 아니라, 우리가 삽입한 UI가 기존 페이지의 조작을 방해하지 않는지도 함께 확인해야 한다는 것을 배웠습니다.

## 글자를 키웠는데, 새로고침하면 돌아갔다

글자 크기를 바꾸는 기능은 현재 페이지의 요소에 스타일을 적용하는 것에서 시작했습니다. 하지만 이렇게 바꾼 스타일은 새로고침하면 사라졌습니다. 페이지가 다시 로드되면서 요소가 새로 만들어지기 때문에, 사용자는 같은 설정을 다시 선택해야 했습니다.

이를 해결하기 위해 사용자가 선택한 값을 저장하는 처리와, 그 값을 페이지에 적용하는 처리를 나눴습니다. 글자 크기와 굵기, 화면 모드를 변경하면 브라우저 저장소에 기록하고, 페이지가 로드될 때 저장된 값을 불러와 다시 적용하도록 했습니다.

새로고침에 대응하고 나니, 페이지를 처음 불러올 때만 설정을 적용하는 것으로는 부족했습니다. 쇼핑 페이지에서는 나중에 콘텐츠가 추가되기도 하고, 사이트가 기존 요소의 스타일을 다시 지정하기도 했습니다. 처음 보이던 글자는 커졌는데 새로 나타난 글자는 그대로라면 읽기 환경이 일정하게 유지되지 않았습니다.

이 변화에는 `MutationObserver`로 대응했습니다. 새로운 요소가 추가되면 해당 요소와 그 안의 적용 대상을 찾아 저장된 글자 설정을 반영했습니다. 기존 대상 요소의 스타일이 변경됐을 때도 글자 크기와 굵기를 다시 적용하도록 했습니다.

기능을 끄고 켜는 동작도 따로 생각해야 했습니다. 잠시 기능을 껐다는 이유로 선택한 설정까지 지우면, 다시 켰을 때 처음부터 값을 맞춰야 합니다. 그래서 사용자가 선택한 설정값과 현재 적용 여부를 분리했습니다. 기능이 꺼져 있을 때는 화면이 바뀌어도 자동으로 재적용하지 않고, 다시 켜면 저장된 설정을 적용하도록 구성했습니다.

초기화는 여기서 한 단계 더 필요했습니다. 저장된 값을 기본값으로 바꾸더라도, 페이지에 이미 적용한 스타일이 남아 있으면 화면은 그대로일 수 있었습니다. 따라서 초기화할 때는 저장값을 변경하면서 확장 프로그램이 삽입한 스타일시트와 관련 인라인 스타일도 제거하도록 했습니다.

설정을 바꾼 뒤 페이지를 새로고침해, 같은 값을 다시 선택하지 않아도 읽기 설정이 유지되는 것을 직접 확인했습니다.

다만 화면 변화가 잦으면 감지와 재적용 작업도 반복될 수 있는 구조였습니다. 다시 만든다면 설정값을 메모리에 보관하고, 변경된 요소 중 실제로 처리가 필요한 대상만 골라 불필요한 작업을 줄이고 싶습니다.

스타일을 해제하는 방식에도 한계가 있었습니다. 관련 인라인 속성을 제거하는 것만으로는 해당 요소가 원래 갖고 있던 값까지 정확하게 복원하기 어려웠습니다. 다음에는 변경 전 값을 기록하거나 별도로 삽입한 스타일시트 중심으로 적용하는 방식을 검토하고 싶습니다. 사용자의 읽기 설정을 유지하는 것만큼, 기능을 껐을 때 원래 페이지로 돌아갈 수 있도록 만드는 일도 필요했습니다.

## 같은 쿠팡 페이지인데, 코드가 달랐다

쿠팡에 기능을 적용하면서 상품 정보를 가져오는 일부터 예상대로 풀리지 않았습니다. 자동으로 정보를 수집하려고 시도했을 때는 접근이 막히는 화면을 만나기도 했습니다. 당시의 정확한 오류나 차단 조건은 남아 있지 않아 원인까지 설명하기는 어렵지만, 필요한 정보를 원하는 방식으로 가져오는 데 제약이 있었습니다.

확장 프로그램에 구현된 상품 정보 수집은 사용자가 열어둔 페이지를 읽는 방식이었습니다. 상품 상세 영역의 HTML을 추출해 VOIM 서버로 보내고, 리뷰 요약에 필요한 리뷰 수와 별점, 본문도 페이지의 DOM에서 가져왔습니다.

그런데 같은 상품 페이지를 확인해도 기기나 확인 시점에 따라 코드가 다르게 보였습니다. 한 번 바뀐 구조로 계속 유지되는 것도 아니고, 두 종류의 구조가 번갈아 나타나는 것처럼 보였습니다. 눈으로는 같은 정보를 보고 있어도, 코드에서 그 정보를 찾는 기준은 같지 않았습니다.

리뷰 수집 코드에도 이 차이가 남아 있습니다. 처음에는 `.review-star-search-selector`를 기준으로 별점 영역을 찾았지만, 이후에는 `.sdp-review__article__order__star__option`도 찾도록 수정했습니다. 전체 리뷰 수와 별점별 개수, 리뷰 본문을 가져오는 선택자에도 두 구조를 함께 처리하는 코드를 추가했습니다.

```javascript
const reviewElements = document.querySelectorAll(
    ".review-content, .sdp-review__article__list__review__content",
);
```

요소가 아직 나타나지 않은 상황에도 대응해야 했습니다. 필요한 요소를 바로 찾지 못하면 `MutationObserver`로 DOM 변화를 지켜보며 일정 시간 기다리도록 했습니다. 페이지에 정보가 없는 경우와, 아직 로드되지 않은 경우를 구분할 필요가 있었기 때문입니다.

두 구조를 지원하도록 수정했지만, 쿠팡이 어떤 조건으로 각각의 구조를 보여주는지까지 확인하지는 못했습니다. 따라서 기기나 시간대가 직접적인 원인이었다고 단정할 수는 없습니다. 당시에는 관찰한 두 형태에 대응하는 방식으로 구현했습니다.

이 경험을 통해 외부 페이지의 DOM을 기준으로 동작하는 기능은 사이트 구조가 달라질 때 영향을 받는다는 것을 겪었습니다. 다시 만든다면 어떤 구조에서 어떤 정보를 읽었는지 기록하고, 정보를 찾지 못했을 때 빈 결과와 추출 실패를 구분하고 싶습니다. 두 형태의 HTML을 테스트 자료로 남겨, 수집 코드를 수정한 뒤에도 각각에서 필요한 정보를 가져오는지 확인하고 싶습니다.

## Tab으로 들어갔다가, 어디로 돌아와야 할까

VOIM의 설정 메뉴에는 글자 크기나 화면 대비처럼 사용자가 직접 조절하는 항목들이 있었습니다. 키보드로 이 메뉴를 이용하려면, 메뉴를 여는 것부터 원하는 설정으로 이동하고 조작한 뒤 돌아오는 과정까지 이어져야 했습니다.

메뉴가 열린 상태에서 `Tab`을 누르다가 포커스가 뒤쪽 쇼핑 페이지로 빠지면 사용자는 설정 위치를 다시 찾아야 합니다. 세부 설정을 닫았을 때도 포커스가 어디로 이동했는지 알기 어려우면 다음 조작을 이어가기 힘듭니다. 그래서 메뉴 안의 이동과 패널을 닫은 뒤의 복귀를 함께 구현했습니다.

먼저 전체 설정 메뉴에는 포커스 트랩을 적용했습니다. 메뉴를 열면 내부에서 키보드로 조작할 수 있는 요소를 찾아 첫 번째 요소로 포커스를 옮겼습니다. 마지막 요소에서 `Tab`을 누르면 첫 번째 요소로, 첫 번째 요소에서 `Shift + Tab`을 누르면 마지막 요소로 이동하도록 했습니다. 설정을 조작하는 동안 포커스가 뒤쪽 페이지로 빠지지 않게 한 것입니다.

세부 설정 패널에는 다른 규칙이 필요했습니다. 패널마다 포커스를 내부에만 가두면, 한 설정을 조절한 뒤 다른 메뉴로 이동하기 어려워질 수 있었습니다. 전체 메뉴 안에서는 이동을 유지하면서, 세부 패널과 메뉴 사이에는 이동 경로를 연결해야 했습니다.

세부 설정을 열면 패널 컨테이너로 포커스를 옮기고, `Tab`으로 첫 번째 조작 요소에 진입하도록 했습니다. 첫 요소에서 `Shift + Tab`을 누르면 해당 설정의 메뉴 버튼으로, 마지막 요소에서 `Tab`을 누르면 다음 메뉴 버튼으로 이동하도록 했습니다. 마지막 메뉴의 패널에서는 설정 초기화 버튼으로 이어지게 했습니다. 이 처리는 `useFocusManagement` 훅으로 분리해 여러 패널에서 공통으로 사용했습니다.

패널을 닫은 뒤에는 사용자가 조작하던 위치로 돌아갈 수 있어야 했습니다. 마지막으로 선택한 메뉴와 각 메뉴 버튼의 참조를 저장하고, `Esc`로 세부 패널을 닫으면 그 패널을 열었던 메뉴 버튼으로 포커스를 돌려줬습니다. 사용자는 돌아온 위치에서 다른 설정을 이어서 선택할 수 있었습니다.

구현 후에는 직접 키보드로 메뉴를 조작했습니다. 전체 메뉴의 처음과 끝에서 포커스가 순환하는지, 세부 패널을 `Esc`로 닫았을 때 해당 메뉴 버튼으로 돌아오는지 확인했습니다.

## 처음 해보는 개발을 마치고

처음에는 Chrome 확장 프로그램 개발을 잘 해낼 수 있을지 걱정됐습니다. 다른 사이트 위에 UI를 띄우고 페이지를 바꾸려면, React로 화면을 만드는 것 외에도 각 코드의 실행 공간과 메시지 통신을 익혀야 했습니다. 복지센터에서 검색부터 구매까지 함께 진행하며, 이런 작업이 실제 쇼핑 과정에서 어떤 도움을 줄 수 있는지도 확인했습니다.

클릭 무반응의 원인을 끝까지 좁히지 못한 점과, 직접 확인한 조작 흐름을 자동 테스트로 충분히 남기지 못한 점은 아쉽습니다. 그래도 낯선 환경에서 작은 동작부터 구현해 나가며 새로운 개발에 도전할 용기를 얻었습니다. 다음에는 구현 결과와 함께 문제가 어디서 발생했는지 확인한 근거도 남기고 싶습니다.
