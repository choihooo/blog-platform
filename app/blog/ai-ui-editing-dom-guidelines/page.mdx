위 데모는 ‘다음’을 누르며 요소 선택, 수정 요청 저장, 구현 결과 확인과 승인 과정을 살펴볼 수 있습니다. 회사에서 개선했던 AI UI 수정 도구도 이런 흐름으로 사용했습니다. 실제 도구에서는 검수 중 수정이 더 필요하면 반려할 수도 있었습니다. 데모는 직접 만든 가상 화면으로 승인까지의 흐름을 옮긴 것이며, 실제 AI를 호출하지는 않습니다.

당시 저는 사용자가 고른 요소를 DOM과 연결해 수정 대상을 확인하고, 공통 작업 지침을 정리하는 일을 맡았습니다. 화면에서 버튼을 고르는 일은 간단해 보이지만, 그 요청을 코드에 반영하려면 확인할 것이 더 있었습니다. 어떤 요소를 바꿔야 하는지 알아야 했고, 같은 스타일을 쓰는 다른 버튼이나 마우스를 올렸을 때의 상태까지 바뀌지 않도록 해야 했습니다.

사용자가 고른 대상과 원하는 변경을 AI에 어떻게 전달해야 할지 궁금했습니다. 화면 사진만으로 충분할까요? DOM을 함께 주면 수정 범위까지 정확하게 지킬 수 있을까요?

그때 다뤘던 문제를 개인 예제로 다시 살펴봤습니다. 회사 코드와 화면은 사용하지 않고 직접 만든 화면 두 개로 실험했습니다. GLM-4.6V에 요청과 사진을 주고, DOM과 작업 지침을 차례로 추가하며 조건마다 다섯 번씩 실행했습니다. 실험에서는 모델이 만든 CSS를 한 번 적용한 결과를 검사했습니다. 모델이 직접 브라우저에서 결과를 확인하고 고치는 과정은 제공하지 않았습니다.

사진만 받은 모델은 실제 코드에 없는 선택자를 만들었습니다. DOM을 주자 간단한 버튼 수정은 다섯 번 모두 성공했지만, 중첩된 화면에서 버튼 상태와 적용 범위까지 유지하도록 하자 DOM과 일반 지침을 함께 줘도 전체 검증을 통과하지 못했습니다. 원하는 버튼을 찾은 뒤에도 어떤 문제가 남았는지 살펴보겠습니다.

## 사진에는 선택자가 보이지 않습니다

첫 실험에는 위 데모와 같은 형태의 프로필 설정 화면을 사용했습니다. 이름·소개·연락처 오른쪽에 같은 모양의 ‘수정’ 버튼을 배치했습니다.

데모에서 소개 버튼을 골라 요청을 작성하듯, 소개 영역의 수정 버튼 하나만 배경 `#FF6F0F`, 글자 `#FFFFFF`로 바꾸도록 요청했습니다. 실험에서는 전달하는 정보에 따른 차이를 보기 위해 다른 버튼과 화면은 그대로 두고, 기존 페이지에 덧붙일 CSS만 답하게 했습니다.

사람은 사진에서 소개 문장 옆의 버튼을 찾을 수 있습니다. 이 버튼에 적용할 CSS를 쓰려면 실제 HTML에서 어떤 요소인지도 알아야 합니다. 사진에 보이는 문구나 위치만으로 클래스명과 상위 요소의 속성까지 알기는 어렵습니다. 같은 화면도 HTML은 서로 다르게 만들 수 있습니다.

요청과 사진만 줬을 때는 이런 CSS가 나왔습니다.

```css
/* 소개 영역의 수정 버튼만 스타일 변경 */
.profile-card .intro-section .edit-btn {
  background-color: #FF6F0F;
  color: #FFFFFF;
}
```

색상은 요청한 값이었지만 원본에는 이 클래스들이 없었습니다. 선택자에 해당하는 요소는 0개였습니다. CSS를 적용해 봐도 화면은 바뀌지 않았습니다.

다섯 번 모두 원본에 없는 선택자를 만들었고, 추가 정보를 요청한 응답은 없었습니다. 그중 한 응답에는 소개 버튼만 바뀔 것이라는 설명도 붙었습니다.

여기서는 필요한 정보가 없을 때 모델이 어떻게 답하는지를 봤습니다. DOM을 요청할 수도 있었지만 다섯 번 모두 선택자를 추정해서 코드를 만들었습니다. 사진만 준 경우와 DOM까지 준 경우는 가진 정보가 다르므로, 이 결과로 코딩 능력을 비교할 수는 없습니다.

## DOM을 제공하자 5번 모두 성공했습니다

이번에는 같은 요청과 사진에 화면의 `main` DOM을 함께 넣어봤습니다. 데모에서 요소를 선택하면 실제 선택자가 표시되지만, 이 실험에서는 DOM을 읽고 모델이 직접 선택자를 만들도록 했습니다. 소개 영역은 이렇게 생겼습니다.

```html
<section class="setting-row" data-ui="row-b" aria-labelledby="field-b">
  <div class="field">
    <h2 id="field-b">소개</h2>
    <p class="value">웹 인터페이스를 만드는 개발자입니다.</p>
  </div>
  <button class="edit-button" type="button">수정</button>
</section>
```

DOM은 브라우저가 다루는 문서 구조입니다. DOM을 보면 ‘소개’라는 텍스트와 수정 버튼이 같은 영역에 묶여 있습니다. 이 영역은 `data-ui="row-b"`로 다른 영역과 구분할 수 있습니다.

한 응답에서는 아래 CSS를 만들었습니다.

```css
[data-ui="row-b"] .edit-button {
  background-color: #FF6F0F;
  color: #FFFFFF;
}
```

이 선택자는 소개 버튼 하나만 가리켰습니다. 적용해 보니 두 색상만 바뀌었고, 함께 검사한 다른 요소의 속성과 위치·크기는 그대로였습니다.

작업 지침도 붙여봤습니다. 요청과 DOM을 대조하고, 공통 클래스를 쓰는 다른 요소까지 바꾸지 않으며, 요청한 속성만 수정하도록 했습니다. 기존 식별 속성을 쓰고 확실하지 않으면 질문하라는 내용도 넣었습니다. 여러 지침을 한꺼번에 넣어서 어느 항목이 영향을 줬는지는 따로 알 수 없습니다.

프로필 화면에서 소개 버튼의 두 색상만 요청대로 바뀌고, 함께 검사한 다른 요소의 속성과 위치·크기가 그대로인 경우를 성공으로 셌습니다.

| 전달한 정보 | 성공 횟수 |
| --- | --- |
| 요청 + 사진 | 0/5 |
| 요청 + 사진 + DOM | 5/5 |
| 요청 + 사진 + DOM + 작업 지침 | 5/5 |

이 화면에서는 지침을 추가해서 달라진 결과가 없었습니다. 기본 상태만 검사했기 때문에 hover나 키보드 포커스에서도 의도대로 동작하는지는 따로 확인해야 했습니다.

## 상태 보존까지 요구하자 오류가 남았습니다

간단한 버튼 수정이 성공했다고 해서 실제 검수에서도 그대로 통과할 수 있을지는 별개의 문제였습니다. 상태와 적용 범위를 더 확인하기 위해 두 번째로 프로젝트 승인 요청 목록 화면을 만들었습니다. 오로라·바다 프로젝트 아래에 운영팀·디자인팀이 있고, 같은 이름과 ‘승인’ 버튼이 여러 번 등장합니다. 중첩된 래퍼와 `.btn__x7` 같은 공유 클래스, 숨긴 미리보기 복제본도 넣었습니다.

이름만 보고 수정 대상을 짐작하기 어렵도록 클래스와 ID도 일부러 구성했습니다. `.btn__x7`은 여러 버튼이 공유하는 클래스이고, `approve-R-17`은 특정 버튼의 ID입니다. 이름에 담긴 의미에 기대지 않고 DOM의 상하 관계와 주변 내용을 읽어 대상을 찾는지 보고 싶었습니다. 대상을 구분할 수 있는 ID와 data 속성은 남겼습니다.

오로라 프로젝트 운영팀에서 대기 중인 김민지의 승인 버튼 하나를 바꿔달라고 했습니다. 다른 과제에서는 같은 팀의 이서준 버튼도 함께 바꾸되 화면 너비가 768px 이상일 때만 적용하도록 요청했습니다.

두 요청 모두 hover·focus-visible·disabled 스타일과 다른 버튼, 숨긴 미리보기는 그대로 두도록 했습니다. DOM을 주는 조건에서는 기존 CSS가 들어 있는 전체 예제 HTML을 프롬프트에 넣었습니다.

요청한 기본색으로 바뀌면서 나머지 상태도 그대로여야 성공으로 봤습니다. DOM만 주거나 일반 지침을 더해도 두 과제 모두 한 번도 전체 검증을 통과하지 못했습니다. 일반 지침을 준 경우에는 과제마다 응답 시간이 초과된 실행이 한 번씩 있었고, 나머지 응답은 CSS를 적용해 보니 문제가 있었습니다.

첫 화면과 비교하면 요청도 달라졌고 검사한 범위도 넓어졌습니다. 앞의 5/5와 여기의 0/5 차이가 DOM이 복잡해졌기 때문이라고만 볼 수는 없습니다.

버튼 하나를 바꾸는 과제에서 DOM만 받은 응답은 다섯 번 중 네 번 기본 상태를 맞췄습니다. 하지만 hover 색상을 새로 정하거나 우선순위가 높은 규칙으로 비활성 상태의 색상까지 덮어썼습니다.

기본색을 바꾸려고 추가한 선택자는 hover 중에도 계속 일치할 수 있습니다. 기존 상태 규칙보다 우선순위까지 높으면 hover 색상도 덮어씁니다. 이 경우를 단순하게 줄이면 아래와 같습니다.

```css
/* 기존 상태 규칙 */
.btn__x7:hover {
  background-color: #e5e7eb;
  color: #111827;
}

/* 뒤에 추가한 규칙은 hover 중에도 일치하고 우선순위도 더 높다. */
[data-record="R-17"] .btn__x7[data-action="approve"] {
  background-color: #FF6F0F;
  color: #FFFFFF;
}
```

수정할 요소를 잘못 찾은 응답도 있었습니다. CSS 표준 선택자가 아닌 `:contains()`를 쓰거나, 프로젝트와 팀 속성을 같은 요소에 있는 것처럼 붙였습니다.

```css
/* 두 속성이 같은 요소에 있어야 일치한다. */
[data-project="aurora"][data-team="ops"]

/* 이 예제에서는 팀이 프로젝트의 하위 요소다. */
[data-project="aurora"] [data-team="ops"]
```

일반 지침에 ‘기존 우선순위를 확인하고 다른 상태를 보존하라’고 적어도 이런 오류가 남았습니다.

## CSS 작성 전략을 지침에 추가했습니다

이 결과를 보고 CSS를 작성하는 방법까지 지침에 적어봤습니다. 비표준 텍스트 선택자를 피하고, 서로 다른 상위 요소의 속성은 자손 관계로 연결하도록 했습니다. 요청한 두 색상만 선언하고, hover·focus-visible·disabled 상태에서는 기본색 규칙이 일치하지 않게 하라는 내용도 넣었습니다. 아래 패턴을 예시로 보여줬습니다.

```css
.sample-control:not(:hover):not(:focus-visible):not(:disabled)
```

`.sample-control`은 설명용 이름이고, 응답에는 DOM에 실제로 있는 대상의 선택자를 쓰도록 했습니다. 앞선 실패를 바탕으로 CSS 작성 전략을 구체화한 후속 실험입니다.

각 과제를 다섯 번씩 실행하고 앞선 결과와 비교했습니다. 대상의 색상이 바뀌고, 함께 검사한 나머지 상태와 속성도 그대로인 경우만 성공으로 셌습니다.

보완 지침은 첫 실패를 보고 만든 탐색적 후속 실험입니다. 앞선 조건과 같은 시점에 진행한 독립적인 대조 실험은 아니고, 제공자와 서버 상태도 같게 맞추지는 못했습니다. 응답 시간이 초과된 실행도 다섯 번에 포함했습니다. 일반 지침에서는 과제마다 한 번씩, 보완 지침에서는 단일 버튼에서 한 번, 복합 조건에서 두 번 최종 응답을 받지 못했습니다.

단일 버튼에서는 응답을 받은 네 번 중 세 번이 전체 검증을 통과했습니다. 그중 하나가 아래 CSS입니다.

```css
#approve-R-17:not(:hover):not(:focus-visible):not(:disabled) {
  background-color: #FF6F0F;
  color: #FFFFFF;
}
```

이 선택자로 이번에 검사한 상태에서 새 규칙이 끼치는 영향을 줄일 수 있었습니다. 다만 `:active`나 부모 요소의 상태는 제외하지 않습니다. 미디어 쿼리와 기존 CSS의 명시도(specificity)·캐스케이드에 따라서도 결과가 달라지므로, 다른 화면에 쓸 때는 그 화면의 상태와 스타일을 다시 확인해야 합니다.

버튼 두 개와 너비 조건을 함께 준 과제에서는 보완 지침을 넣어도 성공하지 못했습니다. 응답을 받은 세 번 모두 프로젝트·팀 속성을 같은 요소에 있는 것처럼 연결했습니다. 일부 응답은 상태를 제외하는 패턴을 썼지만, 선택자가 대상을 가리키지 못해 색상은 바뀌지 않았습니다. 단일 버튼 과제에서 남은 한 응답도 같은 이유로 실패했습니다.

## 정보가 부족하면 질문하도록 했습니다

두 번째 화면에서 버튼 하나를 바꾸는 요청으로, DOM 없이 지침만 추가해 보는 실험도 했습니다. 요청과 사진만 준 경우에 더해 ‘근거가 부족하면 선택자를 지어내지 말고 필요한 정보를 질문하라’는 지침을 붙인 경우를 비교했습니다. 지침을 붙일 때는 CSS 대신 질문으로 답해도 된다고 적었습니다.

사진만 준 다섯 번은 모두 실제 DOM에 없는 선택자를 만들었습니다. 한 응답에는 추정한 구조이니 실제 HTML에 맞게 바꿔야 한다는 설명이 붙었지만, 추가 정보를 물어보지는 않았습니다.

질문을 허용하자 네 번은 CSS를 만드는 대신 추가 정보를 요청하며 수정을 멈췄습니다. 일부 질문에서는 화면의 프로젝트와 팀을 혼동했습니다.

불확실할 때 질문하라는 지침과 질문을 허용하는 출력 형식을 함께 바꿨기 때문에, 어느 쪽이 응답을 바꿨는지는 따로 알 수 없습니다. 다섯 번 중 한 번은 여전히 선택자를 추정했습니다.

## 선택자 검사와 적용 후 검증

이 결과를 데모의 흐름에 대입해 보면, 요청을 저장하고 구현 결과를 검수하는 사이에 확인해야 할 것들이 보입니다. 요청을 저장할 때는 사용자가 고른 요소와 그때의 캡처·DOM을 함께 남기고, 구현 단계에서는 생성한 선택자가 그 요소를 가리키는지 먼저 검사해야 합니다. 데모에는 사용 흐름만 담았지만, 실제 도구라면 이런 검사를 거친 결과를 사용자에게 보여주도록 하겠습니다.

### 적용 전에 대상부터 대조하기

버튼 하나를 바꾸는 요청에서는 먼저 선택자가 요소 하나만 가리키는지, 그 요소가 사용자가 고른 버튼인지 확인할 수 있습니다. 코드를 간단히 쓰면 아래와 같습니다.

```javascript
function assertSingleTarget(selector, selectedElement) {
  if (!selectedElement.isConnected) {
    throw new Error("화면이 변경됐습니다. 수정 대상을 다시 선택해 주세요.");
  }

  let elements;
  try {
    elements = selectedElement.ownerDocument.querySelectorAll(selector);
  } catch {
    throw new Error("유효한 CSS 선택자가 아닙니다.");
  }

  if (elements.length !== 1) {
    throw new Error("수정 대상을 하나로 특정할 수 없습니다.");
  }

  if (elements[0] !== selectedElement) {
    throw new Error("사용자가 선택한 요소와 일치하지 않습니다.");
  }

  return elements[0];
}
```

실험 평가 코드와 별개로, 도구에 넣을 선택자 검사 절차를 간단히 작성했습니다. 일반 문서에서 선택자 하나와 요소 하나를 대조하는 예시이며, 여러 요소를 바꾸는 요청이나 Shadow DOM에서는 검사할 대상과 탐색 범위를 다르게 잡아야 합니다.

이렇게 하면 존재하지 않는 클래스나 다른 버튼을 가리키는 선택자를 걸러낼 수 있습니다. 다만 앞에서 문제가 됐던 높은 우선순위의 규칙도 이 검사는 통과할 수 있습니다. 대상이 맞는지 확인한 뒤에도 CSS를 적용한 결과는 따로 봐야 합니다.

### 대상을 찾은 다음에는 영향 범위 검사하기

대상이 맞으면 격리된 미리보기에서 생성한 CSS를 적용하고, 요청한 속성이 바뀌었는지와 나머지 속성이 그대로인지 확인하도록 하겠습니다. 이번에 검사한 hover·포커스·비활성 상태와 화면 너비뿐 아니라, 요청에 `:active`나 부모 상태가 관련돼 있다면 그 상태까지 확인해야 합니다.

요청을 저장한 뒤 구현을 시작하기까지 화면이 달라질 수도 있습니다. 캡처한 뒤 DOM이 바뀌었다면 선택자가 요소 하나를 가리키더라도 같은 대상을 뜻하는지 다시 확인해야 합니다. 실제 소스를 고치는 도구에서는 그 DOM을 만든 컴포넌트와 다른 사용 위치까지 찾아봐야 합니다. 이번에는 CSS를 덧붙여서 실험했기 때문에 소스 수정이나 다른 화면에 미치는 영향은 확인하지 않았습니다.

선택한 대상이 없거나 여러 개라면 정보를 다시 수집하거나 사용자에게 물어보도록 하겠습니다. CSS를 적용한 뒤 기존 상태가 달라졌다면 검수 전에 수정이 필요하다는 사실을 표시해야 합니다.

데모에서 구현 결과를 확인한 뒤 승인하는 것처럼, 실제 도구에서도 사용자가 변경 내용과 검사 결과를 함께 보고 판단할 수 있어야 합니다. 수정이 더 필요할 때는 반려한 이유와 이전 구현 이력을 남겨두면 다음 수정에서 무엇을 다시 확인해야 하는지도 알 수 있습니다. 버튼의 색상이 바뀌었다는 사실만으로 요청이 끝났다고 판단하기는 어려웠습니다.
