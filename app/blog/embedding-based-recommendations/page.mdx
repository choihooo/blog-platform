블로그 스터디를 운영하다 보면 읽을 글이 계속 쌓입니다. 스터디원이 작성한 글도 있고, 함께 보면 좋을 외부 아티클과 컨퍼런스 콘텐츠도 있습니다.

블로그 스터디 운영을 위한 웹사이트를 개발하고 유지보수하면서, 이렇게 모인 글을 각자의 관심사에 맞게 추천하는 기능을 개선했습니다. 그 과정에서 겪었던 문제와 해결한 방법을 이야기해보겠습니다.

글을 모으는 것에서 더 나아가, 각자의 관심사에 맞는 글을 보여주고 싶었습니다. 기존 외부 콘텐츠 추천은 사용자와 글에 붙은 태그를 비교했습니다. React에 관심이 있는 사람에게 React 태그가 붙은 글을 먼저 보여주는 방식입니다.

구현도 간단하고 추천 이유도 분명했습니다. 그런데 실제 데이터를 넣어보니, 관심사에 맞는 글을 놓치는 경우가 보였습니다. 스터디원이 작성한 글은 최신순과 인기순으로만 볼 수 있어서, 관심사에 맞는 글을 찾으려면 사용자가 목록을 직접 살펴봐야 했습니다.

## 관심 있는 내용인데 태그가 달랐습니다

외부에서 가져오는 글에는 태그가 없는 경우가 있었습니다. 제목과 설명을 읽으면 어떤 주제인지 알 수 있는데도, 태그를 기준으로 추천하다 보니 이런 글은 뒤로 밀렸습니다.

태그가 있다고 모두 해결되는 것도 아니었습니다. 사용자는 LLM을 관심사로 등록했는데, 글에는 embedding이나 vector search라는 태그만 붙어 있을 수 있습니다. 서로 관련 있는 주제지만 글자가 일치하지 않으니 추천에서 연결하기 어려웠습니다.

태그를 더 꼼꼼하게 붙이는 방법도 있겠지만, 추천할 때 제목과 설명도 활용하고 싶었습니다. 사용자가 등록한 단어와 정확히 같지 않아도, 읽어볼 만한 내용을 찾을 수 있어야 한다고 생각했습니다.

그래서 사용자 취향과 글의 의미가 얼마나 가까운지 비교하는 방식으로 바꿨습니다. 여기에 사용한 것이 임베딩입니다. 텍스트를 의미를 비교할 수 있는 숫자 묶음으로 바꾸는 방식입니다.

## 기존 서비스에 임베딩 서버를 연결했습니다

웹은 Vercel에서, 글 수집과 스터디 운영을 맡는 봇은 AWS EC2에서 실행하고 있었습니다. 사용자와 글 정보는 Supabase에 저장했습니다. 여기에 임베딩을 만드는 서버를 연결하고, DB에 벡터를 저장해 비교할 수 있도록 pgvector를 추가했습니다.

임베딩은 GCE VM에 올린 Ollama에서 `nomic-embed-text` 모델로 생성했습니다. 봇의 요청은 Cloudflare Access에서 서비스 토큰으로 인증한 뒤, Tunnel을 거쳐 VM 안의 Ollama에 도착합니다. 생성된 벡터는 봇이 받아 DB에 저장합니다.

사용자가 추천 목록을 열 때마다 임베딩 서버를 다시 호출하지는 않습니다. 글이나 프로필이 바뀔 때 미리 만들어 둔 벡터를 웹에서 비교해 추천합니다.

## 글을 비교하기 전에 입력부터 정리했습니다

임베딩을 쓰기로 했지만, 무엇을 넣어서 비교할지부터 정해야 했습니다. 사용자 관심사에는 짧은 단어 몇 개가 있고, 글에는 제목과 설명이 있습니다. 이 정보를 어떻게 묶느냐에 따라 비교할 수 있는 내용도 달라집니다.

사용자는 관심사에 파트와 자기소개를 더했습니다. 예를 들어 관심사에 React가 있더라도, API와 DB 성능을 좋아하는 백엔드 개발자라는 정보가 함께 있으면 취향을 더 구체적으로 표현할 수 있습니다.

외부 글은 제목과 설명을 기본으로 삼고, 태그와 출처가 있으면 함께 넣었습니다. 태그가 없어도 제목과 설명으로 비교할 수 있도록 했습니다. 스터디원이 작성한 글에는 작성자의 파트와 관심사도 활용했습니다. 글 설명이 짧을 때 이를 보완하기 위해서입니다.

외부 글은 다음처럼 제목과 설명, 태그, 출처를 묶어 임베딩에 넣었습니다.

```txt
Title: React Server Components 성능 최적화
Description: Streaming과 cache 전략 정리
Tags: React, Performance
Source: Frontend Weekly
```

이렇게 정리한 텍스트로 임베딩을 만들어 저장했습니다. 같은 내용으로 매번 다시 만들 필요는 없으니, 입력 내용이 달라졌는지도 확인하도록 했습니다.

처음에는 임베딩을 붙이면 추천이 달라질 것이라는 생각이 앞섰습니다. 실제로 작업할 때는 모델에 어떤 정보를 보낼지 정리하는 데도 신경을 써야 했습니다.

## 관심사와 가까운 글을 먼저 보여주었습니다

사용자 취향과 글을 비교할 수 있게 된 다음에는 추천 순서를 정했습니다. 기본 기준은 의미가 얼마나 가까운지입니다. 여기에 글이 얼마나 최근에 올라왔는지, 스터디와 얼마나 관련 있는지도 함께 반영했습니다.

최신 글만 계속 위에 두고 싶지는 않았습니다. 조금 오래된 글이라도 사용자의 관심사와 잘 맞으면 추천할 수 있도록 했습니다.

스터디원이 쓴 글은 댓글과 조회, 리액션도 참고했습니다. 같은 파트의 사람이 쓴 글인지도 일부 반영했습니다. 다만 반응이 많은 글이 관심사에 맞는 글을 밀어내지 않도록, 스터디 글에서는 의미 유사도를 먼저 비교하고 나머지 정보로 순서를 보정했습니다.

목록을 이어서 볼 때의 순서도 신경 썼습니다. 최신성은 시간이 흐르면 달라지기 때문에, 다음 페이지를 가져올 때도 처음 목록을 본 시각을 기준으로 계산하도록 했습니다. 읽는 도중에 추천 순서가 흔들리는 것을 줄이기 위해서입니다.

## 추천한 이유도 함께 보여주었습니다

추천 순서를 바꾸고 나니 사용자에게 무엇을 보여줄지도 고민하게 됐습니다. '맞춤 추천'이라는 이름만으로는 어떤 기준으로 글이 올라왔는지 알기 어렵습니다.

그래서 관심사에 맞는 글인지, 최근에 올라온 글인지, 다른 사람들의 반응이 있는지를 카드에서 확인할 수 있게 했습니다. 관심사와 직접 겹치는 키워드가 있다면 그 단어도 이유에 넣었습니다.

예를 들어 React와 성능 최적화가 함께 맞으면 'React, 성능 최적화 관심사에 잘 맞아요'라고 보여줍니다. 관심도와 최신성 같은 점수도 함께 표시해 어떤 정보가 추천에 반영됐는지 볼 수 있도록 했습니다.

이 설명을 만들기 위해 매번 LLM을 호출하지는 않았습니다. 추천 순서를 정할 때 사용한 정보를 문장으로 바꿨습니다. 같은 조건에서는 같은 설명이 나오고, 설명이 실제 추천 기준과 연결되도록 하기 위해서입니다.

예를 들어 관심사와 겹치는 키워드가 있거나 의미 유사도가 일정 기준 이상이면, 해당 정보를 추천 이유에 추가합니다.

```ts
if (matchedKeywords.length > 0) {
  reasons.push(`관심사 ${matchedKeywords.join(', ')}와 연결돼요.`);
}
if (semanticScore !== null && semanticScore >= 0.6) {
  reasons.push('프로필 관심사와 의미적으로 가까운 글이에요.');
}
```

키워드를 잘못 잡는 경우도 확인했습니다. AI처럼 짧은 영어 단어가 다른 단어의 일부로 들어 있다는 이유만으로 관심사와 일치한다고 판단하면, 엉뚱한 추천 이유를 보여줄 수 있습니다. 단어의 경계를 확인하도록 하고 관련 테스트를 추가했습니다.

추천 이유를 보여주기로 한 만큼, 그 문장에 들어가는 키워드도 조심해서 다뤄야 했습니다.

## 추천 때문에 글 등록이 느려지면 곤란했습니다

추천을 실제 서비스 흐름에 넣을 때는 임베딩을 만드는 시점도 고민했습니다. 사용자가 프로필을 수정하면 취향을 다시 반영해야 하고, 새 글이 올라오면 그 글도 추천에 포함해야 합니다.

그때마다 임베딩이 완성될 때까지 기다리게 하면 문제가 생깁니다. 임베딩 서버가 느리거나 모델을 처음 불러오는 동안, 사용자는 프로필 저장이나 글 등록을 기다려야 합니다. 임베딩 생성에 실패한 것이 저장 자체의 실패처럼 보일 수도 있습니다.

프로필 저장과 글 등록은 먼저 처리하도록 했습니다. 사용자에게 응답을 보낸 뒤 별도로 임베딩 갱신을 요청합니다. 웹 서버가 직접 임베딩을 만들지 않고 봇 서버에 작업을 맡기도록 했고, 요청이 끝없이 기다리지 않도록 시간 제한도 두었습니다.

<RefreshFlow />

이때 Next.js의 `after()`를 사용했습니다. 응답을 보낸 뒤 실행할 작업을 등록하는 기능입니다. 프로필을 저장한 뒤에는 다음 함수로 갱신을 예약했습니다.

```ts
export function scheduleMemberPreferenceEmbeddingRefresh(memberId: string): void {
  after(async () => {
    try {
      await postToBot('/api/internal/embedding/member-preference', { memberId });
    } catch (error) {
      console.error('[embedding-refresh] 멤버 취향 임베딩 갱신 실패:', error);
    }
  });
}
```

이렇게 분리하면 임베딩 갱신이 실패했을 때 다시 채울 방법이 필요합니다. 추천에 필요한 정보가 아직 없는 데이터와 갱신에 실패한 데이터를 찾아 처리하는 백필 스크립트를 함께 만들었습니다. 이전부터 쌓여 있던 글과 사용자 정보도 이 방법으로 추천에 포함할 수 있습니다.

사용자 취향 임베딩이 아직 없으면 외부 콘텐츠는 기존 태그 방식으로, 스터디 글은 최신순으로 보여주도록 했습니다. 새 추천에 필요한 정보가 모두 준비되지 않았더라도 글 목록을 볼 수 있게 한 것입니다. 태그는 검색 필터와 추천 이유에도 계속 사용했습니다.

## 두 화면에 맞춤 추천을 더했습니다

외부 콘텐츠를 모아 보는 화면에는 맞춤 탭을 추가했습니다. 전체·컨퍼런스·아티클처럼 종류별로 보던 목록에 사용자 취향을 반영한 순서가 생겼습니다.

스터디원이 작성한 글에도 최신순·인기순과 함께 추천순을 추가했습니다. 본인이 작성한 글은 추천 대상에서 제외하고, 두 화면 모두 추천 이유와 점수를 함께 보여주었습니다.

기존에 등록된 사용자와 글의 임베딩도 일괄 생성했습니다. 새로 들어오는 글뿐 아니라, 이미 쌓여 있던 글에도 맞춤 추천을 적용했습니다.

구현 과정에서는 임베딩에 넣을 텍스트가 정해진 규칙대로 만들어지는지, 관심사 키워드를 잘못 잡지는 않는지, 추천 이유가 예상대로 나오는지 확인하는 테스트를 추가했습니다. 예를 들어 관심사를 React와 성능 최적화로, 제목을 'React 성능 최적화 가이드'로 넣으면 'React, 성능 최적화 관심사에 잘 맞아요.'라는 설명이 나오는지 확인했습니다. 태그를 추론하는 과정에서도 허용된 관심사 안에서 결과가 나오는지 확인했습니다.

## 추천 점수와 읽고 싶은 글 사이에 남은 차이

입력과 추천 이유가 정한 규칙대로 만들어지는지는 테스트했습니다. 다만 이 테스트만으로 사용자가 실제로 읽고 싶은 글을 추천한다고 판단할 수는 없습니다. 같은 React 글이라도 입문 내용을 찾는 사람과 특정 성능 문제를 해결하려는 사람에게 필요한 글은 다를 수 있습니다.

작성자 정보를 활용한 선택에도 한계가 있습니다. 글 설명이 짧을 때 작성자의 파트와 관심사로 맥락을 보완했지만, 이 정보가 글 자체의 주제보다 강하게 반영될 수 있습니다. 작성자의 관심사는 사용자와 비슷해도, 그 사람이 이번에 쓴 글까지 관심사에 맞는다는 보장은 없습니다. 실제로 얼마나 발생하는지는 더 확인해야 합니다.

다시 개선한다면 사용자와 추천 목록을 함께 보며 읽고 싶은 글과 관련성이 낮다고 느끼는 글을 구분해보고 싶습니다. 관련성이 낮은 글에서는 제목·설명과 작성자 정보 중 무엇이 영향을 줬는지 살펴보고, 작성자 정보를 넣는 범위나 최신성·인기의 비중을 조정하려고 합니다.

조정 전후에는 같은 사용자 정보와 같은 글 목록으로 결과를 비교할 계획입니다. 관련성이 낮았던 글의 순위가 내려가는지와 함께, 기존에 유용했던 추천도 유지되는지 확인하고 싶습니다.
