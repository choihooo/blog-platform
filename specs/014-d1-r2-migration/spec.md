# Feature Specification: d1-r2-migration

**Feature Branch**: `[014-d1-r2-migration]`

**Created**: 2026-07-31

**Status**: Draft

**Input**: User description: "Supabase에서 D1 + R2 기반 블로그로 이관. 댓글은 유지하지 않고 글 중심, 주 1~2개 발행, 이미지(WebP) 중심, 비용은 경량 운영, 3일 내 단계적 전환."

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 기존 공개 게시글이 그대로 노출됨 (Priority: P1)

방문자는 기존처럼 동일한 글 URL로 접속해 글 목록과 상세 페이지를 읽을 수 있어야 한다.

**Why this priority**: 블로그 핵심 가치가 읽기 경험이므로, 이주 직후라도 글 열람이 안 되면 서비스 가치가 즉시 상실된다.

**Independent Test**: 기존에 발행된 공개 글 5개를 새 URL 체계로 조회해 본문 제목·본문·날짜가 정상 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 발행된 글이 존재하고 기존 Slug가 유지된 상태에서, **When** 방문자가 해당 Slug URL에 접속하면, **Then** 이전과 동일한 공개 전용 글 정보(썸네일, 제목, 본문, 발행일)가 표시된다.
2. **Given** 초안/보관 상태의 글이 존재할 때, **When** 동일한 URL로 접근하면, **Then** 공개 목록/상세에서는 노출되지 않고 적절한 비노출 처리(404 또는 비공개 메시지)가 유지된다.

### User Story 2 - 본문 이미지와 썸네일이 끊김 없이 노출됨 (Priority: P1)

방문자는 이전 포스팅에 포함된 본문 이미지가 손상 없이 표시되어야 하며, OG 이미지/썸네일도 정상 노출되어야 한다.

**Why this priority**: 콘텐츠 중심 블로그에서 이미지 노출이 깨지면 SEO/SNS 공유/가독성이 동시에 저하된다.

**Independent Test**: 마이그레이션 대상 글 3개를 대상으로 본문 내 이미지 10개를 점검해, 이미지가 모두 로드되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 이미지 URL이 새 미디어 저장소 키로 치환된 게시글, **When** 글 상세 페이지를 렌더링하면, **Then** 썸네일, 본문 이미지, OG 이미지가 모두 노출된다.
2. **Given** 이미지 업로드 실패가 발생한 항목이 있어도, **When** 이관 로그를 기준으로 대체 키 또는 누락 처리 정책을 적용하면, **Then** 게시글 상세는 깨진 링크를 노출하지 않고 정상 텍스트 렌더링이 유지된다.

### User Story 3 - 관리자 글 편집 플로우가 계속 동작함 (Priority: P2)

운영자는 기존 CMS 인터페이스에서 새로 운영되는 스토리지/DB 구조를 인식하지 못해도 글 작성·수정·삭제를 계속 수행할 수 있어야 한다.

**Why this priority**: 운영자가 매일 발행 루틴을 중단하지 않아야 전환 리스크를 낮출 수 있다.

**Independent Test**: 게시글 1건을 등록/수정/삭제하고, 각 동작 후 목록과 상세에서 결과가 즉시 반영되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자 대시보드에서 새 글 작성 화면에 접속하면, **When** 글을 발행 상태로 저장하면, **Then** 해당 글이 목록·상세에 즉시 반영된다.
2. **Given** 작성된 글의 이미지를 교체하면, **When** 저장 후 재조회 시 새 이미지가 우선 노출되고 이전 미디어는 교체 정책에 따라 보존/관리된다.

### User Story 4 - 전환 후 이슈 시 빠른 롤백이 가능함 (Priority: P3)

운영자는 문제 발생 시 설정 변경만으로 기존 방식으로 되돌릴 수 있어야 한다.

**Why this priority**: 7일 이중 보관 기간 동안 안정성을 검증해야 하므로 즉시 복구 경로가 필수다.

**Independent Test**: 이슈를 가정한 뒤 환경변수/라우팅 스위치로 즉시 이전 데이터 소스로 회귀해 글 조회가 정상 동작함을 확인한다.

**Acceptance Scenarios**:

1. **Given** 게시글 조회 API에서 이슈가 감지되면, **When** 롤백 스위치를 1분 이내에 적용하면, **Then** 기존 콘텐츠 조회 방식으로 즉시 복귀한다.
2. **Given** 롤백 기간 동안에도 신규 데이터가 소량 생성되었을 때, **When** 복귀 후 동기화된 이중 보관(최소 7일)이 존재하면, **Then** 데이터 불일치 없이 운영이 지속된다.

### Edge Cases

- 업로드 키 충돌이나 slug 중복이 발생했을 때 우선순위(기존 글 보호, 충돌 감지, 알림) 정책은 어떻게 적용하는가?
- Supabase 객체 메타데이터가 누락되거나 이미지 링크에 상대 경로가 섞여 있을 때 치환 실패를 어떻게 감지하고 재처리하는가?
- 이주 기간 중 관리자 임시 비정상 동작(동시 수정, 삭제, 재발행) 충돌 시 최종 상태 규칙은 무엇인가?
- 카테고리의 깊이가 1차/2차를 넘는 데이터가 유입될 때 마이그레이션 정지 규칙은 무엇인가?
- read/write API가 타임아웃(2.5s/5s/15s) 경계에 동시에 걸릴 때 장애 등급 판정과 롤백 유예/즉시복구 기준은?

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 블로그 운영 정책은 “구조화 데이터와 미디어를 분리”해야 하며, 구조화 데이터는 읽기/조회 중심의 경량 SQL 저장소로, 바이너리 파일은 객체 저장소로 분리되어야 한다.
- **FR-002**: 구조화 데이터는 글(post), 태그(tag), 글-태그 연결(post_tag), 미디어 참조(media_ref), 관리자 계정(admin), 공개 설정값 등의 최소 모델을 포함해야 한다.
- **FR-003**: 모든 공개 글 접근 URL은 기존 slug 규칙을 유지해 기존 링크와 SEO 경로를 깨뜨리지 않아야 한다.
- **FR-004**: 본문 내 이미지 URL은 마이그레이션 결과 생성된 미디어 키로 일괄 치환되며, 치환 누락 항목은 탐지 로그가 남아야 한다.
- **FR-005**: 이미지 키/URL 생성 규칙은 연·월·슬러그 기준 구조를 따라, 기존 버전관리와 교체/삭제 이력을 추적할 수 있어야 한다.
- **FR-006**: 마이그레이션 파이프라인은 다음 순서를 보장해야 한다. 1) 태그/글-태그 매핑, 2) 글 본문/메타 적재, 3) 미디어 참조 저장.
- **FR-007**: 데이터 적재·미디어 업로드 중 실패 항목은 재시도 규칙을 따라 자동 복구를 시도하고, 미해결 항목은 재시작 가능 목록으로 남아야 한다.
- **FR-008**: 전환 초기에 최소 1개 샘플 글을 대상으로 구버전/신버전 동시 조회를 수행해 조회 결과 정합성을 검증해야 한다.
- **FR-009**: 관리자 기능(작성/수정/삭제)은 외부 사용자 흐름을 바꾸지 않고 동일 UI/경로에서 동작해야 하며 내부 저장소 접근은 어댑터 계층으로 추상화되어야 한다.
- **FR-010**: 운영 중 이슈가 발생하면 1분 이내에 라우팅/환경 스위치로 이전 방식으로 되돌리는 롤백 경로를 제공해야 한다.
- **FR-011**: 전환 완료 후 최소 7일간 이중 보관(레거시 백업/저장소 보존)을 유지해야 한다.
- **FR-012**: 일일 모니터링 지표는 조회량 일치율, 이미지 노출율, 에러율을 포함하며, 누락 시 점검 알림이 가능해야 한다.
- **FR-013**: 카테고리는 1차/2차 계층을 지원해야 하며, `parent_slug` + `slug`로 계층 경로가 재현 가능해야 한다.
- **FR-014**: 카테고리 계층은 `/categories/[categoryPath]` 또는 `/categories/[depth1]/[depth2]`로 조회 가능해야 한다.
- **FR-015**: 새로 이관되는 모든 게시글은 카테고리 참조가 있을 때 2차 카테고리(자식 카테고리)에 매핑해야 하며, 최상위 카테고리만 있는 게시글도 처리 가능해야 한다.
- **FR-016**: 모든 공개 API는 API 계약 문서된 타임아웃, 재시도 정책을 적용해야 하며, 실패 시 재시도 가능한 항목과 불가능 항목을 분리해 리포트해야 한다.
- **FR-017**: 조회 API p95 응답시간은 listPosts 600ms, getPostBySlug 500ms, getPostsByTag/getPostsByCategoryPath 700ms 이내여야 한다.
- **FR-018**: write API p95 응답시간은 createPost 1.2s, updatePost 1.5s, deletePost 1.2s 이내여야 하며 upsertMediaRef는 2s 이내여야 한다.
- **FR-019**: API는 1분 롤백 시나리오에도 1회차 장애 후 dual-run/복구 지연 없이 1분 이내 공개 장애를 복귀할 수 있어야 한다.

### Key Entities

- **Post (글)**: 게시글 본문, 제목, slug, 발행/수정 시각, 공개 여부, 요약, 조회수 등의 기본 속성을 가진 핵심 객체.
- **Tag (태그)**: 글의 분류 기준으로 쓰이는 레이블 정보와 slug를 가진 객체.
- **Post Tag Mapping (글-태그 연결)**: 글과 태그의 다대다 관계를 관리하는 연결 정보.
- **Media Reference (미디어 참조)**: 썸네일, 본문 이미지, OG 이미지 등 파일 기반 미디어의 저장 위치와 용도 정보를 보존하는 참조.
- **Admin (관리자)**: 글 작성·수정·삭제 권한을 가진 운영자 신원 정보와 활동 추적용 최소 속성을 가진 객체.
- **Category (카테고리)**: 1차/2차 계층 카테고리 정보와 부모-자식 관계를 보존하는 객체.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 전환 1주일 이내 공개 글 목록/상세 조회 정합성(기존 대비 노출 실패 없는 URL 비율)이 99.5% 이상이어야 한다.
- **SC-002**: 대상 이미지 포함 게시글에서 본문 이미지 및 썸네일 노출 성공률이 99.8% 이상이어야 한다.
- **SC-003**: 관리자 글 생성·수정·삭제의 성공 완료율이 99% 이상이어야 하며, 인터페이스 변경 없이 운영자가 1일 1~2회 발행 루틴을 유지해야 한다.
- **SC-004**: 핵심 이슈(조회 실패, 이미지 실패, 저장 실패)가 감지될 때 롤백이 1분 이내로 완료되어 공개 장애가 5분 연속 0건이 된다.
- **SC-005**: 전환 후 30일 내 추가 운영비용이 기존 예산 대비 계획된 경량 구간을 유지해야 하며, 비용 증가가 미리 정의한 비용 상한을 넘지 않아야 한다.
- **SC-006**: 2차 카테고리 경로(`depth1/depth2`)의 카테고리 페이지에서 상위/하위 카테고리별 글 목록 일치율이 99.5% 이상이어야 한다.
- **SC-007**: API 응답 성능 기준 만족: `listPosts` p95 600ms, `getPostBySlug` p95 500ms, `getPostsByTag`/`getPostsByCategoryPath` p95 700ms, write API p95 1.5s 이내.
- **SC-008**: 서비스 안정성 기준 만족: read timeout 2.5초, write timeout 5초, 업로드 timeout 15초, 요청 성공 후 첫 10개 연속 호출에서 `retryable-failure` 5% 초과 금지.
- **SC-009**: 재시도 정책 수행율: `retryable-failure`는 최대 3회 재시도 후 실패가 판정되고, 재시도 실패 항목 100%가 재처리 큐로 남아야 한다.

## Assumptions

- 댓글 기능은 현재 스펙에서 제외되며, 향후 기능 추가 시 별도 스펙으로 다뤄야 한다.
- 글은 주 1~2개 발행하는 단일 운영자 중심 운영 패턴으로 진행한다.
- 미디어는 WebP 이미지를 중심으로 관리하며, 핵심 손실 요인은 이미지 경로/노출이다.
- 이관 전후 7일간은 기존 방식과 새 방식의 동시 보관 기간을 적용해 되돌릴 수 있어야 한다.
- 관리자 인터페이스는 현재 사용 중인 화면/운영 방식을 유지하는 것이 우선이다.
- 카테고리는 1차/2차 계층을 지원하며, 최대 2단계만 허용한다.
