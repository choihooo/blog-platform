# 기능 명세: Content Model

**Feature Branch**: `main`

**Created**: 2026-07-30

**Status**: Draft

**Input**: 사용자 설명: "로드맵의 두 번째 작업인 Phase 1 Content Model을 구현한다."

## 사용자 시나리오 및 테스트 _(필수)_

### 사용자 스토리 1 - 파일 기반 콘텐츠 구조 확정 (Priority: P1)

블로그 운영자로서, repository 안에 글, 작성자, 사이트 설정, 카테고리, 태그를 담는 표준 콘텐츠 구조를
갖추고 싶다. 그래야 공개 블로그, CMS, SEO 산출물이 같은 파일 원본을 기준으로 동작할 수 있다.

**우선순위 근거**: MVP의 핵심 전제는 GitHub repository가 콘텐츠 원본이라는 점이다. 콘텐츠 구조가
먼저 확정되지 않으면 렌더링, CMS 편집, 발행, SEO 작업이 같은 기준으로 개발될 수 없다.

**독립 테스트**: repository에서 콘텐츠 폴더와 필수 샘플 파일을 확인하고, 각 파일이 문서화된 콘텐츠
역할을 충족하는지 검증해 독립적으로 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 콘텐츠 모델 phase가 완료된 repository가 있을 때, **When** 운영자가 `content/` 영역을
   확인하면, **Then** 글, 작성자, 카테고리, 태그, 사이트 설정 파일이 예측 가능한 위치에 존재한다.
2. **Given** 샘플 글과 운영자 프로필이 있을 때, **When** 이후 공개 블로그나 CMS 작업자가 콘텐츠
   원본을 찾으면, **Then** 별도 데이터베이스나 외부 CMS 없이 repository 파일만으로 시작할 수 있다.

---

### 사용자 스토리 2 - 상태별 글 검증 (Priority: P2)

블로그 운영자로서, 초안, 발행 글, 보관 글이 서로 다른 필수 정보를 요구하기를 원한다. 그래야 미완성
글은 안전하게 저장하면서도 공개되는 글은 제목, slug, 작성자, 발행일, 본문을 갖추도록 보장할 수 있다.

**우선순위 근거**: 공개 블로그와 자동 산출물은 `published` 콘텐츠만 사용한다. 상태별 검증이 명확해야
초안이나 불완전한 글이 독자에게 노출되는 위험을 줄일 수 있다.

**독립 테스트**: 상태별 frontmatter 조합과 본문 유무를 바꿔 유효한 콘텐츠와 거부되어야 하는 콘텐츠를
각각 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** `published` 상태의 글이 제목, slug, 작성자, 발행일, 본문 중 하나를 누락했을 때,
   **When** 콘텐츠 검증을 실행하면, **Then** 해당 글은 공개 가능한 콘텐츠로 인정되지 않는다.
2. **Given** `draft` 상태의 글이 아직 slug를 갖지 않았을 때, **When** 콘텐츠 검증을 실행하면,
   **Then** 로컬 편집 가능한 초안으로 인정된다.
3. **Given** 허용되지 않은 `status` 값을 가진 글이 있을 때, **When** 콘텐츠 검증을 실행하면,
   **Then** 해당 글은 명확한 검증 실패로 처리된다.

---

### 사용자 스토리 3 - 저장 및 발행 전 slug 정책 검증 (Priority: P3)

블로그 운영자로서, 글을 저장하거나 발행할 때 제목에서 예측 가능한 slug가 만들어지고 기존 글과
충돌하지 않기를 원한다. 그래야 URL 충돌 없이 글을 관리하고 이후 공개 라우팅과 SEO 산출물을
안정적으로 생성할 수 있다.

**우선순위 근거**: slug는 공개 URL, RSS, Sitemap, canonical metadata의 기준이 된다. 중복 slug가
허용되면 공개 페이지와 생성 산출물이 불안정해진다.

**독립 테스트**: 제목 기반 slug 생성 결과와 전체 글 목록 기준 중복 검사를 확인해 독립적으로 검증할
수 있다.

**Acceptance Scenarios**:

1. **Given** slug가 없는 초안과 유효한 제목이 있을 때, **When** 저장 또는 발행 전 콘텐츠 정책을
   적용하면, **Then** 제목을 기반으로 공개 URL에 사용할 수 있는 slug 후보가 제공된다.
2. **Given** 같은 slug를 가진 글이 이미 존재할 때, **When** 새 글을 저장 또는 발행하려 하면,
   **Then** 중복 slug가 거부되고 운영자가 충돌을 해소할 수 있는 실패 사유가 제공된다.

### Edge Cases

- `content/posts/` 안에 비어 있는 본문을 가진 `published` 글이 있으면 공개 가능한 글로 인정하지
  않아야 한다.
- `publishedAt` 값이 없거나 날짜로 해석할 수 없으면 `published` 글 검증에 실패해야 한다.
- 작성자 ID가 존재하지 않는 운영자 프로필을 참조하면 콘텐츠가 완전한 공개 글로 인정되지 않아야 한다.
- 카테고리나 태그 설정에 없는 값을 글이 참조하면 검증 실패 또는 명확한 경고로 처리되어야 한다.
- 제목이 slug로 변환하기 어려운 문자만 포함할 경우 저장 또는 발행 전에 사람이 이해할 수 있는 slug
  대안이 필요하다는 실패 사유를 제공해야 한다.
- 보관 글은 repository에 남아 있을 수 있지만 공개 콘텐츠 목록과 자동 산출물의 대상이 되어서는 안
  된다.

## 요구사항 _(필수)_

### Functional Requirements

- **FR-001**: repository는 `content/` 아래에 글, 작성자, 카테고리, 태그, 사이트 설정을 위한 파일
  기반 콘텐츠 영역을 제공해야 한다.
- **FR-002**: repository는 최소 하나의 샘플 글과 단일 운영자 프로필을 제공해 이후 렌더링, CMS, SEO
  작업이 실제 콘텐츠 형태를 기준으로 검증될 수 있게 해야 한다.
- **FR-003**: 사이트 설정은 사이트 이름, 사이트 URL, 기본 작성자, 관리자 GitHub identity, 콘텐츠
  repository 위치, analytics provider, AI assistant flag, internal link suggestion flag를 표현해야
  한다.
- **FR-004**: 글 frontmatter는 `draft`, `published`, `archived` 상태만 허용해야 한다.
- **FR-005**: `published` 글은 제목, slug, 작성자, 발행일, 비어 있지 않은 본문 없이는 공개 가능한
  콘텐츠로 인정되어서는 안 된다.
- **FR-006**: `draft` 글은 slug 없이도 로컬 편집 가능한 콘텐츠로 인정될 수 있어야 한다.
- **FR-007**: `archived` 글은 repository에 보존될 수 있지만 공개 콘텐츠와 생성 산출물의 대상으로
  분류되어서는 안 된다.
- **FR-008**: 콘텐츠 검증은 상태별 필수 field 누락, 허용되지 않은 상태, 누락된 발행일, 빈 발행 본문,
  작성자 참조 오류를 구분 가능한 실패로 보고해야 한다.
- **FR-009**: 저장 또는 발행 전 정책은 제목 기반 slug 후보를 만들고 전체 글 목록 기준 중복 slug를
  거부해야 한다.
- **FR-010**: 카테고리와 태그는 별도 설정 파일에서 관리되어야 하며, 글이 참조하는 분류 값은 설정된
  값과 대조할 수 있어야 한다.
- **FR-011**: 콘텐츠 모델은 공개 블로그가 런타임에 로컬 콘텐츠 파일만 읽는 MVP 경계를 지원해야 하며,
  별도 CMS 데이터베이스나 object storage를 요구해서는 안 된다.
- **FR-012**: 콘텐츠 모델은 이후 Markdown/MDX 변환, CMS editor round-trip, SEO scoring, RSS,
  Sitemap, JSON-LD, OG image 생성이 같은 콘텐츠 metadata를 사용할 수 있도록 안정적인 입력 계약을
  제공해야 한다.

### 주요 Entity

- **Post**: 블로그 글을 나타내는 콘텐츠 단위. 상태, 제목, slug, 작성자, 발행일, 요약, cover image,
  카테고리, 태그, 본문을 가진다.
- **Draft Post**: 아직 공개 준비가 끝나지 않은 글. slug와 발행일이 없을 수 있으며 로컬 편집 대상으로
  남을 수 있다.
- **Published Post**: 독자에게 공개될 수 있는 글. 제목, slug, 작성자, 발행일, 비어 있지 않은 본문이
  필수다.
- **Archived Post**: repository에는 보존되지만 공개 목록과 생성 산출물에서 제외되는 글.
- **Author**: 글의 작성자를 나타내는 프로필. MVP에서는 단일 운영자 프로필을 기준으로 한다.
- **Site Config**: 사이트 이름, URL, 기본 작성자, 관리자 GitHub identity, 콘텐츠 repository 위치,
  analytics provider, 기능 flag를 담는 설정.
- **Category**: 글을 넓은 주제 단위로 분류하기 위한 관리 목록.
- **Tag**: 글을 세부 주제나 키워드 단위로 분류하기 위한 관리 목록.

## 성공 기준 _(필수)_

### Measurable Outcomes

- **SC-001**: 신규 contributor가 repository를 연 뒤 2분 이내에 글, 작성자, 분류, 사이트 설정 콘텐츠
  위치를 식별할 수 있다.
- **SC-002**: 상태별 검증 테스트가 필수 field 누락, 잘못된 상태, slug 중복, 누락된 발행일, 빈 발행
  본문 사례를 100% 구분해 성공 또는 실패로 판정한다.
- **SC-003**: 샘플 `published` 글은 콘텐츠 검증을 통과하고 이후 공개 블로그 렌더링 입력으로 사용할
  수 있다.
- **SC-004**: slug 중복 검사는 전체 글 목록 기준으로 충돌 사례를 매번 거부한다.
- **SC-005**: 공개 콘텐츠 대상 목록에는 `published` 상태 글만 포함되고 `draft` 및 `archived` 글은
  제외된다.
- **SC-006**: 콘텐츠 모델 산출물은 MVP에서 금지한 별도 CMS 데이터베이스, object storage, 다중 작성자
  권한, 예약 발행을 도입하지 않는다.

## 가정

- feature scope는 콘텐츠 파일 구조, 샘플 콘텐츠, 사이트 설정, 상태별 검증, slug 정책으로 제한한다.
- MVP 작성자는 단일 운영자이며 다중 작성자 권한과 승인 flow는 포함하지 않는다.
- 실제 CMS editor UI, GitHub write mutation, 공개 라우트 렌더링, SEO 산출물 생성은 이후 phase에서
  다룬다.
- 사이트 설정의 관리자 GitHub login과 immutable user ID는 실제 운영 값으로 교체 가능한 placeholder로
  시작할 수 있다.
- 카테고리와 태그는 MVP에서 repository 안의 관리 파일을 기준으로 검증한다.
