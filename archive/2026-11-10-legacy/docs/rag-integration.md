## Gemini 전환 구현 — 2026-11-06

Gemini 임베딩·서버 생성 경로를 추가했다. 기본값은 기존 Workers AI·브라우저 Kanana이며 아직 운영
전환·재임베딩을 수행하지 않았다. Gemini는 별도 768차원 인덱스와 Worker secret을 사용한다. 현재
설정·검증·롤백은 [Gemini runbook](./runbooks/2026-11-06-gemini-rag.md), 앱 간 계약은
[RAG API 계약](../specs/016-gemini-rag/contracts/rag-api.md)을 따른다. 아래의 과거 `sync` 실행
예시는 현재 CLI에서 dry-run이다. 실제 쓰기는 명시적 실행 옵션이 필요하다.

최신 검색·후속 질문 개선 및 525개 임베딩 점검 결과는
[RAG 품질 개선 기록](./rag-quality-improvements.md)을 참고한다. 아래에는 초기 연결과 이전 실험

## 현재 상태

코드 연결과 실데이터 검색을 완료했다. 첫 브라우저 3문항 검증에서 회사 간 업무 혼동을 발견했고,
**경력·성과 질문을 구조화된 원문 답변으로 전환한 뒤 같은 3문항 재검증을 통과했다.** 일반 RAG 생성
답변의 모든 환각을 해결한 것은 아니며 광범위한 운영 품질 검증은 남아 있다.
`hochoi8621.workers.dev`와 기존 도메인은 변경하지 않았다.

- D1 `blog-platform`: 공개 글 33개 확인. 기존 테이블/글 수정 없음.
- Vectorize `hozorica-portfolio-rag`: 1024차원, cosine, 공개 코퍼스 임베딩 524개 업로드 완료.
- Worker 배포, 기존 hozorica.com 교체, 요금제 변경 없음.
- 미리보기: http://localhost:3001 (3000의 기존 실험 서버는 유지).

## 데이터 흐름

질문 → Next `/api/rag` → 인증된 Worker `/search` → Workers AI BGE-M3 임베딩 → Vectorize → 현재 공개
원문 대조 → 브라우저 Kanana Q8 답변 + 원문 링크.

- 답변 생성 모델은 기존 브라우저 Kanana 2 1.3B Q8 그대로다. 서버에서 답변을 생성하지 않는다.
- 검색 질문은 서버와 Cloudflare로 전달된다. 대화 전체와 기존 AI 답변은 검색 요청에 포함하지 않는다.
  애플리케이션에서 대화/질문을 DB에 저장하지 않는다. 인프라의 표준 운영 메타데이터 로그는 별개다.
- API 토큰은 Next 서버 및 Worker에만 둔다. Wrangler OAuth 자격 증명은 읽거나 복사하지 않았다.
- 개발용 앱 인증 토큰 2개를 무작위 생성해 gitignore 대상 `.dev.vars`, `.env.local`에만 저장했다. 이
  토큰은 Cloudflare 계정 API 키가 아니다.

## 검색 대상과 안전장치

- D1의 `is_published = 1`인 글 본문·요약. 기존 editor의 본문 파서를 재사용한다.
- 기존 프로젝트 9개: 설명·역할·기술·성과·본문. 이미지/영상 바이너리 및 코드 블록은 검색하지 않는다.
- 이력서의 경력·사이드 프로젝트·기술·활동·수상. `resume-data.ts`로 기존 배열을 이동해 화면과 검색이
  동일 데이터를 사용한다. 아직 별도 JSX에 있는 학력·자격증·자기소개 전체를 추출한 것은 아니다.
- 최대 500자 청크, 50자 중첩. 모델·버전·문서 식별자·제목·URL·청크 내용으로 SHA-256 ID를 만든다.
- 매 검색 후 D1 primary 세션으로 공개 원문을 다시 읽고 현재 청크 ID만 통과시킨다. 수정·삭제·비공개된
  오래된 청크 본문을 Vectorize 메타데이터에서 반환하지 않는다.
- 검색 실패/근거 없음이면 모델을 호출하지 않고 안내한다. 조회 오류를 빈 문서로 간주하지 않는다.
- 출처 URL은 내부 공개 경로만 허용한다. 출처와 발췌문은 모델이 아니라 앱에서 표시한다.
- 질문 최대 600자, 요청 본문 최대 4096바이트, 인용 최대 3개, 모델 입력 발췌 총 900자. 문자 제한이며
  정확한 토큰 예산 검증을 대신하지는 않는다.
- Worker 검색은 지역별 aggregate 30회/60초 제한. 분산 전역 비용 상한이나 사용자별 공정성을 보장하는
  제한은 아니다. 운영 트래픽에서는 별도 예산 알림/WAF/사용자별 제한 검토 필요.
- 검색·관리자 토큰 분리 및 timing-safe 비교. 원문/질문/토큰은 앱 오류 로그에 기록하지 않는다.

## 실행과 최초 인덱싱

1. 현재 계정에는 `hochoi8621.workers.dev`가 등록되어 있다. 추가 온보딩은 필요 없다.
2. 저장소 루트에서 아래 실행:

```sh
pnpm --filter @blog-platform/rag-worker dev
pnpm --filter @blog-platform/rag-worker sync
pnpm --filter @blog-platform/blog dev
```

다른 터미널에서 Worker와 웹 서버를 실행한다. 현재 3000이 사용 중이면 웹은
`pnpm --filter @blog-platform/blog exec next dev --port 3001`로 실행한다. 현재 프로덕션 미리보기를
쓰려면 rebuild 후 next start를 사용한다.

Worker는 127.0.0.1:8787에서 실행하고 D1/Vectorize/AI는 원격 바인딩을 사용한다. **로컬 실행이어도
Workers AI/Vectorize 실제 사용량이 발생한다.** 실패 시 유료 플랜으로 자동 변경하지 않는다.

`sync`는 16청크씩 처리하고 기존 ID를 조회해 이미 있는 임베딩 생성을 건너뛴다. 실패하면 처음부터
재실행할 수 있다. 페이지 간 코퍼스가 바뀌면 409로 중단하여 재시작하도록 한다. Vectorize의 반영은
비동기이므로 업로드 직후 검색 검증 전 반영 시간을 고려해야 한다.

## 글 발행·수정 시 갱신

기존 CMS의 public-refresh가 Next `/api/revalidate`에 `/blog/{slug}`를 보내는 흐름에 연결했다. RAG
설정이 있으면 해당 공개 글만 다시 청크화/인덱싱한다. 실패하면 페이지 캐시는 갱신됐음을 알리면서
502를 반환해 기존 새로고침 재시도 경로를 활용한다. 비공개 전환 시 현재 공개 목록에서 빠져 즉시 검색
결과 검증에서 제외된다.

- **CMS가 deploy-hook만 사용하거나 직접 SQL로 D1에 쓰는 경우 이 훅을 통과하지 않는다.** 그 경우
  업로드 스크립트/배포 파이프라인에서 인증된 `/sync`를 호출하거나 full sync 명령을 실행해야 한다.
- 프로젝트/이력서 변경은 Worker 코드에도 포함되므로 Worker 재시작/재배포 후 full sync가 필요하다.
- 오래된 벡터는 현재 ID 검증으로 답변에서 제외하지만 **물리 삭제·GC는 아직 구현하지 않았다.** 변경이
  쌓이면 저장량과 검색 topK에 영향을 준다. 주기적인 전용 인덱스 재구축 또는 manifest 기반 청소가
  다음 작업이다.

## 운영 연결에 남은 일

- 더 다양한 한국어 질문에 대한 검색 정확도 및 카나나의 최종 답변 검증.
- 코사인 컷오프는 실제 smoke test를 보고 0.42에서 0.48로 조정했다. 적은 질문으로 결정한 임시값이므로
  더 큰 평가 세트가 필요하다.
- 작은 모델의 환각이 완전히 방지되는 것은 아니다. 특히 허위 전제 경력 질문, 날짜·수치 답변을 원문과
  비교해야 한다.
- 후속 질문은 현재 질문만 검색한다. “그건?”처럼 문맥만 있는 질문은 명시적인 프로젝트명/기술명으로
  다시 묻도록 안내한다.
- 현재 작은 공개 코퍼스에 맞춰 매 검색 시 공개 글 전체를 읽는다. 규모 증가 시 문서 버전
  manifest/배치 조회로 최적화해야 한다. 1000개 초과 글 또는 단일 문서 100,000자 초과는 명시적으로
  실패한다.
- Worker 배포와 secrets 등록, Next 운영 환경의 `RAG_API_URL`, `RAG_SEARCH_TOKEN`, `RAG_ADMIN_TOKEN`
  설정은 미실행이다. workers.dev 등록만으로 서비스가 배포되지는 않는다.

## 참고

### 글 안내 생성 품질 반복 개선 — 2026-09-06

사용자 재현 질문: “AI에 대해서 쓴 글 있어?” 검색된 AI 글이 있는데도 모델이 없다고 답하는 문제를 실제
브라우저에서 반복 시험했다. 모델은 기존 Kanana 2 1.3B Q8을 유지했고 글 안내용 고정 답변 문구/질문별
정답을 추가하지 않았다.

실험 기록:

1. JSON 대신 제목/소개 중심 자료와 의미 매칭 지시: 긍정 답변으로 바뀌었지만 없는 제목을 만들어 실패.
2. 프롬프트·문맥 축약: 실제 제목을 쓰다가 마지막에 없는 제목을 추가하여 실패.
3. 자료를 user 메시지의 질문 앞에 배치: 단순 존재 질문은 맞았으나 제목 2개·요약 요청에서 글 내용을
   혼동.
4. 글별 문장 출력 지시: 두 글의 내용을 여전히 섞음.
5. **글 안내 요청은 글 하나당 별도 모델 호출로 분리.** 제목은 검색된 원문에서 그대로 표시하고 설명만
   카나나가 생성. 아래 두 주제에서 제목 변조/글 간 혼합 없이 응답 확인.

현재 처리:

- 블로그 결과는 같은 URL의 중복 청크를 제거한다. 후반부/참고문헌이 검색돼도 첫 청크의 글 소개를 함께
  제공한다. 임베딩 재생성 없이 반환 문맥만 개선했다.
- 최대 두 자료, 총 발췌 600자. ‘글/블로그/포스트’가 포함되고 선택 자료가 모두 블로그인 요청은 글별
  독립 생성(각 최대 120 출력 토큰), 다른 일반 질문은 공동 문맥 생성(최대 256 토큰).
- 글 제목은 앱이 원문 그대로 붙이고 내용 설명은 모델이 직접 만든다. 공개 글 안내를 사실 템플릿
  답변으로 대체한 것은 아니다. 기존 경력/성과의 구조화 답변은 유지한다.
- 자료를 system 지시와 분리해 user 문맥에 전달. 이전 AI 답변은 입력하지 않는다. prompt cache는 이
  경로에서 껐다.
- 두 번 순차 생성하므로 한 번의 호출보다 지연이 늘 수 있다. 현재 개발 진단의 토큰 속도/개수는 마지막
  호출 기준이므로 합산 성능 평가에는 별도 보완이 필요하다.

실제 브라우저 최종 응답:

- AI 질문 → 「검증 가능한 AI UI 설계하기」: 인간-AI 상호작용의 신뢰성과 해결 방안 설명. 「AI 시대의
  개인 이슈 트래커 - 나만의 Linear를 만들어봤다」: AI 코딩 시대 개발 업무 변화 설명. 주제 수준의
  안내는 개선됐으나 후자의 제품 구현 세부까지 설명한 것은 아니다.
- React 질문 → 「[React] 리액트 개발 도구를 활용해 좋은 웹 어플리케이션 만들기」: 개발 도구·디버깅
  설명. 「[React] 언제 메모이제이션을 해야할까?」: 메모이제이션 개념과 활용 설명.

### 소유자 이름·별칭 연결 — 2026-09-06

- 사용자 확인에 따라 최호, 호조리카, Hozorica(대소문자 무관)를 동일인으로 처리한다. 다른 이름의 부분
  문자열은 매칭하지 않는다.
- 공개 이력서 소개를 `features/resume/profile-data.ts`로 추출해 이력서 UI와 소개 답변이 같은 원문을
  사용한다. 명시적인 소개·동일인 질문만 구조화 답변으로 처리하며 `/resume` 출처를 제공한다.

  답변으로 대체하지 않는다. 생성 질문에도 정규화한 이름을 사용한다.

  소유자 이름 및 소유 표현을 제거해 주제로 검색하도록 보완했다. 재검사에서 React 개발 도구·React
  Router 글을 반환했다. 다만 React를 예시로 언급한 추천 시스템 글도 상위에 포함되어 검색 순위 개선
  여지는 남는다.
