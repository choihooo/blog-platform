# Kanana Q8 분할 다운로드

## 범위

기존 Kanana 2 1.3B Q8 모델의 가중치를 바꾸지 않고 GGUF 파일만 분할한다. Wllama 3.6.1의
`parallelDownloads: 3`과 기본 브라우저 캐시를 사용한다. UI의 기존 `progressCallback`은 전체 조각의
다운로드 바이트 합계를 받으므로 진행률 계산을 따로 복제하지 않는다.

자동 로딩·채팅 상태 표시는 메인 작업의 `portfolio-chat.tsx` 변경을 그대로 사용하며, 이 작업에서는
수정하지 않았다.

## 로컬 준비

`apps/blog`에서 아래 명령을 명시적으로 실행한다. install/build 단계에서는 대용량 모델을 자동
다운로드하지 않는다.

```sh
node scripts/prepare-kanana-shards.mjs /path/to/llama-gguf-split
```

- 원본: `dummy9996/kanana-2-1.3b-instruct-GGUF`, revision
  `6c998111f40f3ab7adf65620a6a752230d8c75f6`, `kanana-2-1.3b-instruct-Q8_0.gguf`.
- 원본 크기: 1,377,890,688 bytes. SHA-256:
  `0b63b6b68f0c1f0e667ad070808dfee7a03db06fc41c3fe23c9d794841c6f801`.
- 준비 스크립트는 스트림으로 내려받아 원본 크기·SHA-256을 확인한 뒤 `--split-max-size 512M`으로
  분할한다. 임시 다운로드와 결과를 포함해 약 3GB 이상의 여유 공간이 필요하다.
- 결과: `public/models/kanana-q8-0b63b6b68f0c-v1/`에 GGUF 조각 3개와 `manifest.json`. 파일별
  크기·SHA-256, 원본 정보, 전체 tensor 수를 기록한다.
- 생성 디렉터리는 Git에서 제외한다. 기존 결과가 있으면 체크섬을 검증하고 재사용하며 임의로 덮어쓰지
  않는다. 임시 원본은 완료 후 제거한다.
- 개발 모드에서는 이 디렉터리의 첫 파일을 사용한다. 새 체크아웃에서 실행하려면 먼저 준비 명령을
  실행하거나 아래 URL 설정으로 기존 호스트를 지정해야 한다.

## 배포 설정

이번 작업에서는 원격 업로드·환경변수 변경·운영 배포를 하지 않는다. 운영 기본값은 기존 고정
revision의 단일 Hugging Face 파일을 유지한다.

운영에서 분할 파일을 사용하려면 3개 파일을 동일 디렉터리로 호스팅하고 빌드 전에 첫 파일 URL을
지정한다.

```text
NEXT_PUBLIC_KANANA_MODEL_URL=/models/kanana-q8-0b63b6b68f0c-v1/kanana-q8-00001-of-00003.gguf
```

동일 출처 URL이면 현재 CSP를 유지할 수 있다. 별도 CDN을 선택한다면 해당 호스트의 CORS, HEAD/GET,
Content-Length, CSP `connect-src` 허용을 별도로 확인해야 한다. URL에 비밀 토큰을 넣지 않는다. 버전이
바뀌면 디렉터리도 바꿔 캐시 충돌을 피한다. 호스팅 플랫폼의 개별 파일 크기 제한 때문에 Next 정적
배포에 그대로 포함할 수 없는 경우가 있으므로 호스팅 선택은 별도 작업이다.

## 동작과 한계

- 3개 조각을 동시에 받으며 전체 다운로드 완료 후 GPU에 로드한다. 일부 파일만 받은 상태에서 추론을
  시작하는 방식이 아니다.
- 전체 모델 용량·GPU 메모리는 줄지 않는다. 병렬 다운로드의 속도 이득은 네트워크에 따라 달라지며 고정
  배수의 개선을 보장하지 않는다.
- 유효한 분할 모델 캐시가 있으면 다음 로드에서 재사용한다. 기존 단일 파일 캐시와 분할 파일 캐시는
  별개여서 최초 전환 시 한 번 더 다운로드한다. 기존 캐시는 임의로 삭제하지 않는다.
- 취소·실패 후 바이트 단위 이어받기나 누락 조각만 다운로드하는 동작은 이 구현에서 보장하지 않는다.
- 재방문해도 GPU 초기화 시간은 필요하다.

## 검증 기록 — 2026-09-06

- llama.cpp build 10819로 분할 완료. 파일 크기: 516,791,200 / 511,608,032 / 349,491,776 bytes. 텐서
  수: 101 / 149 / 104, 합계 354개로 원본과 일치.
- 준비 명령 재실행 시 다운로드 없이 기존 조각 SHA-256 검증 완료.
- localhost:3001에서 각 파일 HEAD 200, Content-Length 일치, Range GET 206 및 GGUF 헤더 확인.
- 별도 테스트 탭에서 실제 Q8 로드 완료: 9,776ms, GPU 33/33 layers, 모델 버퍼 1,308.88MiB. 이후 React
  글 질문의 실제 생성 답변 및 출처 2개 확인.
- 테스트 탭 새로고침 후 다운로드 100%·GPU 준비 안내 및 입력 비활성화 확인, 준비 완료 후 입력 활성화.
  재로딩 8,725ms. 로컬 파일 기준 1회씩 측정한 값이며 외부 다운로드 속도 비교나 성능 향상 배수로
  해석하지 않는다.
- 테스트 21파일 81개, lint, production build 통과. 운영은 기존 단일 모델 URL 기본값을 유지.
- 메인 브라우저 탭은 조작하지 않았다. Aside 스킬의 기본 위임 경로는 보조 대화의 위임 금지 조건
  때문에 사용하지 않고, 독립된 내장 브라우저 테스트 탭으로 검증했다.

## 단계별 로딩 측정

`kanana-load.ts`는 Wllama의 공개 API를 사용해 기존 URL 로딩 흐름을 캐시 조회 → 필요한 경우 다운로드
→ Blob 열기 → 런타임 로드로 나눈다. 모델·추론 설정·다운로드 동시 개수는 유지한다. 결과는 채팅의 개발
전용 성능 진단 `loadTiming`에서 볼 수 있다.

- `cacheLookupMs`: 유효한 캐시 모델 조회.
- `downloadAndCacheMs`: 네트워크 수신과 캐시 저장을 합한 시간. 캐시 적중이면 0.
- `cacheOpenMs`: 캐시 Blob 핸들 열기. 지연 읽기 특성상 전체 디스크 읽기 시간은 아니다.
- `runtimeAndGpuMs`: 실제 파일 읽기, Worker/WASM 초기화, GGUF 해석, GPU 업로드, 런타임 준비를 포함.
  GPU 업로드만의 시간으로 해석하면 안 된다.
- `totalMs`: 위 흐름 전체 시간. 바깥 UI의 `loadMs`에는 기존 모델 종료·동적 모듈 import 등도
  포함된다.
- `source`, `bytes`, `shards`: 캐시/다운로드 경로와 모델 규모 확인.

개발 전용 `다운로드 포함 로딩 측정 · 1.38GB` 버튼은 캐시가 있어도 같은 모델을 다시 내려받는다.
Wllama는 `downloadModel` 내부에서도 파일 캐시를 재사용하므로, 측정 때만 UUID 쿼리가 붙은 임시 URL을
사용한다. 종료 시 해당 임시 조각만 삭제를 시도하며 정상 모델 캐시는 삭제하지 않는다. 브라우저 강제
종료·저장소 오류·다운로드 취소 경쟁 상황에서는 임시 캐시가 남을 수 있다. 자동 로딩은 계속 기존
캐시를 우선 사용한다. 로드 실패·취소 시 성공 측정값을 남기지 않으며 기존 에러/취소 UI를 사용한다.

초기 재다운로드 실험의 `downloadAndCacheMs: 22`는 실제 전송 없이 하위 파일 캐시를 재사용한 값이므로
다운로드 측정에서 제외했다.

### 단계별 실측 — 2026-09-06

모든 값은 localhost:3001, 현재 Apple WebGPU 환경의 Q8 3조각 기준이다. 외부 CDN·실제 인터넷 회선의
다운로드 측정이 아니며 단일 샘플을 보편적인 성능 수치로 해석하지 않는다.

| 실행                                               | 캐시 조회 | 다운로드+저장 | Blob 열기 | 런타임+GPU 준비 | 단계 합계 |
| -------------------------------------------------- | --------: | ------------: | --------: | --------------: | --------: |
| 최초 캐시 로드(빌드 동시 진행)                     |      38ms |           0ms |      11ms |         8,158ms |   8,208ms |
| 임시 URL 실제 다운로드(빌드 동시 진행)             |      33ms |      11,032ms |      14ms |         8,635ms |  19,714ms |
| 임시 URL 실제 다운로드(빌드 종료 후)               |      19ms |       4,578ms |       5ms |         6,341ms |  10,943ms |
| 정상 캐시 재로드(빌드 종료 후, 런타임 예열된 상태) |      17ms |           0ms |       9ms |         3,441ms |   3,467ms |

임시 다운로드 측정에서는 `totalMs` 이후 정리 시간도 발생한다. 빌드 종료 후 예시의 UI `loadMs`는 기존
모델 종료·모듈 준비·임시 캐시 정리까지 포함해 11,774ms였다. 단계별 값 반올림 때문에 합계에 1ms 정도
차이가 있을 수 있다.

해석: 로컬에서도 런타임 준비 시간이 크고 빌드 동시 실행의 영향이 뚜렷했다. 현재는 3조각을 유지한다.
추가 분할의 이득은 입증되지 않았으며, 운영 호스팅을 정한 뒤 동일 회선에서 다운로드와 저장을 포함해
3조각/6조각을 비교해야 판단할 수 있다.

측정 코드 추가 후 22파일 86테스트, lint, production build 통과.

임시 캐시 정리 후 실제 React 글 질문에 모델이 답변하고 출처 2개를 제공하는 것을 확인했다. 이어 정상
모델 URL을 다시 로드했을 때 `source: cache`, 다운로드 0ms로 기존 캐시 보존을 확인했다. 테스트 전용
탭은 종료했다. 메인 탭·기존 캐시의 일괄 삭제·원격 배포는 하지 않았다.
